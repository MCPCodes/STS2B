# The in-game brain

The mod can play by itself: it calls the Claude Messages API directly with Mark's API key, so nothing runs besides the game. Without a key, or when the API credit, the Console spend limit or the monthly cap runs out, it falls back to Mark's Claude subscription by starting Claude Code headless in the background, which drives the same tools over MCP. Running `/play` in Claude Code by hand still works too, for debugging (type `/stop` in game first, since two players would cancel each other's waits).

## What the player does

1. Once: create an API key in the Claude Console and save it to `~/.config/spiremind/api_key` (one line, `chmod 600`; the README has the Terminal commands). The mod never writes the key anywhere and never logs it. `ANTHROPIC_API_KEY` in the game's environment works too, but the file wins. Then run `scripts/dev-host.sh --brain` to check the key and the API calls without the game (Smoke test, below).
2. In game, type `/start` in the chat. The bot plays from wherever the run stands. `/stop` stops it (no more API calls, Claude Code is told to quit, and an `act_sequence` or `wait_for_decision` still running for it ends). The choice is remembered: after `/start`, the bot starts by itself the next time a run is in progress, also after a restart of the game, until `/stop`. After a restart the chat says who plays when the first run starts. `/start` is refused while another MCP client (a `/play` session by hand) has called a game tool on `/mcp` in the last 30 seconds: stop it there first.
3. Chat works as in `docs/chat.md`. `/pause` and `/resume` still mean "hands off for a moment" and work with either brain.
4. More commands, each answered with a line in the chat:
   - `/budget`: API spend this month and this run, the request count, the model and effort, and what is playing and why.
   - `/model [opus|sonnet|haiku|fable]`: shows the model, or switches it (a full model id works too, if the price table knows it).
   - `/effort [low|medium|high|xhigh|max]`: shows or sets the thinking effort. Without an argument it shows all three: the normal effort and the elite and boss ones.
   - `/effort elite|boss [level|same|default]`: shows or sets the effort in elite or boss rooms (Fight effort, below). `same` follows the normal effort; `default` puts back high-or-the-normal-effort-when-higher.
   - `/fast [on|off]`: shows whether the API's fast mode is on and what it costs, or switches it: answers come up to 2.5 times faster at twice the price (Fast mode, below).
   - `/help` lists them all.

`/start`, `/stop`, `/model` and `/effort` save to config.json; `/fast` never does, and is off again at the next start of the game. A changed model or effort applies from the next request and starts a fresh API conversation: the cache belongs to a model, thinking blocks to the model that wrote them, and a new top-level effort invalidates the cached messages, so a short restart costs less than the old history. A fight effort changed while the bot is in that kind of room counts the same way; changed elsewhere, it waits for the next such room. A normal effort changed during an elite or boss fight whose own effort stays the same waits until the bot leaves the room, and the reply says which rooms keep their own. Claude Code gets the model when a session starts, so while the subscription plays a new model waits for its next session (the reply says so), and the effort never reaches it.

### Fight effort

Elite and boss rooms are played at their own effort, high by default. In a benchmark of 40 real Act 1 fights on Opus, high effort won 12 of 16 elite and boss fights against 9 of 16 at medium, while hallway fights barely changed (mean HP left 53.0 against 51.7); high cost about $0.70 a fight against $0.47 and took 2.1 minutes against 0.8. So the normal effort stays where it is and only the hard rooms pay for more thinking.

- **Which effort** (`BrainSettings.EffortFor`): in an elite room `elite_effort`, in a boss room `boss_effort`, everywhere else `effort`. Left out of config.json, a fight effort is high, or the normal effort when that is higher (normal xhigh keeps xhigh in a boss fight). Set to a level, it is used exactly as chosen, lower than high or lower than the normal effort too: the brain never raises effort past a fight effort the human picked. `same` (or a JSON null) means the normal effort. `/effort low` changes only the normal effort; the default fight effort follows it up when it goes above high.
- **Which requests**: the room comes from the snapshot's `run.room` (the game's RoomType: Monster, Elite, Boss and others), which only combat snapshots carry. A fight room therefore lasts from the first combat snapshot that names it through that room's own later screens (rewards, card reward, card and hand selects, a modal) until a snapshot names another room or shows the map, a shop, rest site, event, treasure, crystal sphere, the menu or game over (`RunScreens.FightRoom`). The rewards are kept on purpose: an elite's relic and a boss's rare cards and relic are among the run's biggest choices, they take only a few requests, and one switch in and one out per room is all it costs. The map is where the bot leaves, so the next room is picked at the normal effort. A treasure screen counts as leaving too: it only exists in a Treasure room, and in co-op a teammate can pick the next room without the bot seeing the map.
- **max_tokens** follows the effort in effect (`MaxTokensFor`), so a boss fight at high gets 32000 even when the normal effort gives 16000. `max_tokens` in config.json still wins.
- **Conversation and cache on a switch** (from the Effort and Prompt caching docs as of October 2026): a top-level `output_config.effort` change invalidates the cached messages, and on models that render the thinking configuration ahead of tools and system it invalidates those caches too; it doesn't invalidate earlier thinking blocks. Opus 5.5, Opus 5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 also take per-message effort: an effort-only system message, `{"role": "system", "content": [], "output_config": {"effort": "medium"}}` under beta `mid-conversation-output-config-2026-07-01`, which may sit anywhere in `messages`, is an append (so the cache and the thinking blocks stay valid) and takes effect from the next user turn with new input. A user turn of `tool_result` blocks alone isn't new input, so in a tool loop like the brain's such a change would wait for one that is. The docs call lowering effort this way reliable, and raising it best for large jumps (low to xhigh). So the brain treats the two directions differently:
  - **Raising** (entering an elite or boss room at the default high, or leaving a room whose chosen effort was lower) starts a fresh conversation at the new top-level effort ("The thinking effort changed with the room..."): the run journal, the recent chat and the state. Medium to high is a one-level raise, the smallest there is, a model reading a history written at the old effort tends to stay at it, and the fresh, short conversation is how the benchmark above played each fight. It is also cheap: every request of the fight re-reads a short history instead of a long one. A conversation that starts inside a fight room for any other reason (a refresh, a refusal, `/start` mid-fight) also takes the fight effort at the top level.
  - **Lowering** (leaving the room, or entering one whose chosen effort is lower) keeps the conversation on those models: one effort-only message goes in just before the user message about to be sent, and that message gets a short note after its tool results ("(You left the Elite room, so the thinking effort is back to medium.)") so it counts as new input and the change applies to that very reply. The top-level effort stays what the conversation started with, every request in a conversation holding such a message sends the beta header, and the model keeps the room's rewards in mind. On a model without per-message effort (Fable 5, or any id not on that list) lowering starts a fresh conversation too, since a top-level change would rebuild the messages cache anyway.
  - **Cost of the top-level effort varying between conversations**: on a model that renders the thinking configuration ahead of tools and system, a fight conversation's first request writes the system prompt and tools at its effort once. That entry has the 1-hour TTL and every read refreshes it, so the next fight within the hour reads it, and the normal-effort entry stays warm the same way: at most one extra system and tools write per effort per idle hour, on those models only.
  - **If the API refuses the effort message**: a 400 on the first request that carries a new effort message, or one whose text names `output_config` or effort, is taken for a refusal of the beta. The brain says so once in the chat, starts a fresh conversation, and lowers effort with fresh conversations (and raises no turn plan, Turn plans below) until the next `/start`. Any other 400 stops the brain as before, even with an effort message in the conversation.
  - **Unverified until the first live elite fight**: whether the fight requests really think at high. They should write noticeably more output tokens and take longer than hallway fights at medium (the benchmark: about $0.70 and 2.1 minutes a fight at high against $0.47 and 0.8 minutes at medium). If they don't, nothing reports it, so check (docs/verify-on-mac.md).
  - Each switch is logged once ("brain: entered the Elite room; effort medium to high, starting a fresh conversation", "brain: left the Elite room; effort high to medium, keeping the conversation"), and transcript entries record the effort each request was sent at.
- **Subscription fallback**: it keeps one effort. Claude Code plays a whole run in one headless session and isn't told an effort at all; changing it per room would mean ending and resuming the session around every elite and boss fight, which reloads the whole context and pauses play, so the fight effort applies to the API brain only.

### Turn plans

Two switches in config.json, both off by default, ask for more deliberation at the start of each player turn in elite and boss rooms. They exist so the arena's real-brain mode can measure whether that wins more fights; off, they change nothing. The reason to try: in Mark's live co-op run the brain thought little per request even at high. A boss room took 48 requests and 17.8K output tokens in all (371 a request on average, 5054 at most), elite requests averaged 215 and hallway requests at medium 154. Nothing caps it (max_tokens is 32000 at high), but each tool call is its own request and adaptive thinking decides per request, so most follow-ups think little.

- **When**: on the user message that carries the first actionable snapshot of a new player turn, in an elite or boss room (the fight room of Fight effort, above). That is a `combat` snapshot with `awaiting_decision` true and actions, whose `state.turn` and `state.round` differ from the last turn marked in this fight. A `hand_select` (mid-turn, or a choice at the start of a turn), busy and waiting snapshots and later snapshots of the same turn don't count; the first actionable snapshot of a fight does. It may come at the top level of a tool result, under `next` or `current`, or in the opening of a fresh conversation. The fight's rewards, or leaving the room, start the count over. Hallway and event fights and everything off combat are never touched.
- **`turn_plan_note`** (true or false): that user message gets one text block at its end, "(New turn. Before your first tool call, plan the whole turn: the enemies' damage this turn and over their next two turns (next_moves), when each enemy dies, and the order of every card and potion. Then play it.)", once per player turn. A request that carried it and got no answer (the API refused its effort message, the prompt was too long, the settings changed while it was retried) or whose reply was thrown away (a refusal, a full context window) hands it on to the next one.
- **`turn_plan_effort`** (a level, or null for none): when it is higher than the room's effort and the model takes per-message effort, an effort-only system message raising effort to it goes just before that user message, which gets a note so it counts as new input: the plan note when `turn_plan_note` is on, else "(New turn: thinking effort is xhigh while you plan it.)". The next request lowers it back to the room's effort the same way ("(Turn planned; thinking effort back to high.)"). When the planning request already ended the turn and the next snapshot is another new turn, the raise stays, with no lowering and raising in between. A raised request's `max_tokens` follows the raised level (`MaxTokensFor`) unless config.json sets `max_tokens`.
  - The top-level effort and the room's effort the brain compares against stay as they were, so the raise never counts as an `/effort` change or a room switch. A room switch in between (leaving the room while raised) takes the place of the lowering and ends at the normal effort, and a fresh conversation starts at the room's effort anyway.
  - On a model without per-message effort, or once the API has refused an effort message, there is no raise and one log line says why: a top-level change would start a fresh conversation every turn. A refused raise costs the one fresh conversation the refusal path above starts, and no raise is tried again until the next `/start`.
  - From the default fight effort (high), `turn_plan_effort` xhigh is a raise of one level, and the docs say raising with an effort message works best for large jumps, so whether the raised requests really think longer is part of what to measure.
- **Cost**: a raised request is meant to think longer, so it writes more output tokens, billed at the output rate ($20 per million on Opus 5.5), and each raise and lowering adds a short note and an effort message to the conversation. The note alone adds a few dozen input tokens a turn plus whatever extra thinking it brings.
- **Records**: each transcript entry's `effort` is the effort that request was sent at (a raised one says `xhigh`), and a request that carried a turn plan (the note or the raised effort) has `"turn_plan": true`, so output tokens per effort can be added up from the transcripts. The fight log's `effort` lists a raised level too.
- The log says each raise and lowering ("brain: new turn in the Elite room; effort high to xhigh for its plan", "brain: turn planned; effort xhigh back to high").

### Fast mode

`/fast on` makes the API brain ask for the API's fast mode: the same model writing its answer at up to 2.5 times the output tokens per second, for twice the price. `/fast off` goes back, and `/fast` alone says whether it is on and what it costs on the model in use. It is a research preview on the Claude API, so the API key's organization needs access to it (Anthropic's fast mode page has the waitlist); without it the first fast request is turned down and the brain carries on at normal speed (When the API says no, below).

- **Off unless asked for.** It is off every time the game starts and lasts until `/fast off` or the game closes. It is the one brain setting that is never saved: `Save` doesn't write it, a `fast` key typed into config.json is ignored with a line in the log, and `/start`, `/stop`, `/model`, `/effort` and a new run, which all read config.json again, keep whatever `/fast` last set. Nothing switches it on but `/fast on`.
- **Models.** Opus 5.5, Opus 5 and Opus 4.8 only (`ModelPrices.FastTable`, dated snapshots of them included); on any other model a request that asks for fast mode is an error, so the brain never sends one there. `/fast on` on another model answers "Fast mode works on Opus 5.5, Opus 5 and Opus 4.8 only, and the model is Sonnet 5.5. It stays off." A `/model` change to a model that doesn't take it switches it off with a line in the reply ("Fast mode is off now: it works on Opus 5.5, Opus 5 and Opus 4.8 only."), and it stays off after a change back. So does a config.json edited by hand to such a model, the next time the file is read. `/model` itself only takes models from the standard price table, so Opus 5 and Opus 4.8 can only come from `model` in config.json, where their standard responses are still priced at the table's highest rates (Settings, below).
- **The request.** With it on, every request carries the top-level field `"speed": "fast"` and the beta flag `fast-mode-2026-02-01` in the `anthropic-beta` header, after any beta the request already names (`mid-conversation-output-config-2026-07-01,fast-mode-2026-02-01` while an effort message is in the conversation). With it off, neither is sent and the request is byte for byte what it was before fast mode existed. Nothing else about the request changes with the speed.
- **A switch mid-run** applies from the next request and keeps the conversation: no fresh one, and the fight effort and turn plan handling don't see it. A request that was being resent when it was typed (the API was unreachable) goes on at the new speed. The API doesn't share cached prefixes between speeds, so the first request after a switch, either way, writes the whole prompt to the cache again, once: a few cents on a short conversation, more on a long one, at the fast write price when switching on. For the other copies' cap check that request is estimated like a conversation's first.
- **When the API says no.** The brain sends the very same request again at once without the speed field, so the turn isn't lost, switches fast mode off (`BrainController.FastDeclined`, so `/fast` and `/budget` say so) and says why once in the chat. Nothing asks for fast mode again until `/fast on`. The standard request is then handled as any request is, so a failure there retries or stops the brain exactly as before, and the two can't loop. It happens for:
  - a 429 that outlasted `ClaudeClient`'s own tries, which wait the `retry-after` the API names each time, or one that asks to wait more than 30 seconds, which the client doesn't wait for in fast mode (`MaxFastRetryAfter`; at standard speed it waits up to 5 minutes). So a rate limited fast request goes again at standard speed after 2 minutes at most. Fast mode has a rate limit of its own, separate from the model's standard one: "Fast mode hit its rate limit; back to normal speed.";
  - a 529 that outlasted them (the fast mode page lists 529 for its capacity too): "Fast mode is out of capacity right now; back to normal speed.";
  - a request the API refuses outright (a 400, 403, 404 or 413) whose message names the speed field, fast mode or its beta flag: "Claude turned down fast mode (a research preview your API key may not have yet); back to normal speed. The details are in the log.";
  - any such refusal of the first fast request since the brain started that names neither fast mode nor an effort message and doesn't say the prompt is too long (how the API words a key without access isn't documented). Such a refusal doesn't say what is wrong, so the try at standard speed decides. Once that try is answered, the same line is said and fast mode goes off. If it is refused too (the request is wrong at any speed, or the API rejects the key), the brain stops or starts a fresh conversation exactly as before, fast mode isn't blamed, nothing is said about it and the setting stays as it was.

  A 401 and the credit and spend limit errors are never taken for fast mode, and any other refusal of a fast request once fast mode has worked stops the brain as it always did, with fast mode left on.
- **What it costs.** A response whose `usage.speed` is `"fast"` is priced from `ModelPrices.FastTable`, whatever the request asked for; one that says `"standard"` at the standard rate (and a fast request answered that way is logged once); one that names neither (no speed, or a word the mod doesn't know) as the request asked, so a fast request is never counted at half its price. Per million tokens (pricing and fast mode pages, 2026-10-12, which list input and output and say the prompt caching multipliers apply on top):

  | Model | Input | 5 minute cache write | 1 hour cache write | Cache read | Output |
  | --- | --- | --- | --- | --- | --- |
  | Opus 5.5, fast | $8 | $10 | $16 | $0.40 | $40 |
  | Opus 5 and Opus 4.8, fast | $10 | $12.50 | $20 | $1.00 | $50 |

  Every rate is twice the model's standard one. A fast response from a model outside that table, which the API shouldn't give, is priced at twice its standard rates. `/budget`, the monthly cap and the fight log's `spent_usd` all count the fast price, and `/budget` and the line that says who plays read "Opus 5.5, high effort, fast mode" while it is on. It is still the mod's own estimate; the Claude Console has what was billed.
- **Records.** Each transcript entry has `speed` (`fast` or `standard`, what its request was sent with) after `effort`, and its `usage` holds the API's own `speed`; a fight's line in the fight log lists the speeds of its requests under `speed`, in order. The log line of a fast response reads `brain: claude-opus-5-5 fast in ...`.
- **Subscription fallback.** Fast mode is the API's. While Claude Code plays, `/fast on` still switches it on for when the API brain plays again, and the reply says Claude Code isn't affected.
- **Co-op.** Typed in Mark's window it goes to every running bot copy like `/model` and `/effort`, each answering under its name; a bot's name first sends it to one (`/fast Silent off`). The relay doesn't carry settings to a bot copy that starts later, and nothing is saved, so a bot added or relaunched after `/fast on` plays at normal speed until `/fast on` is typed again (the bots already fast answer "Fast mode is on already."). A bot's fallback line shows in Mark's chat under its name.
- **Unverified until the first live `/fast on`**: that this key has fast mode at all, the wording of a refusal, and that the fast requests really come back faster (docs/verify-on-mac.md). `scripts/dev-host.sh --brain --model opus --fast` answers the first two without the game (Smoke test, below).
- The arena and the dev host never ask for it by themselves: nothing there sets it but the smoke test's `--fast`.

## Settings

`~/.config/spiremind/config.json`, all optional:

```json
{
  "repo": "/Users/mark/Projects/STS2B",
  "model": "claude-opus-5-5",
  "effort": "medium",
  "elite_effort": "high",
  "boss_effort": "high",
  "monthly_budget_usd": 200,
  "autostart": false,
  "claude_path": "/opt/homebrew/bin/claude"
}
```

`autostart` is what `/start` and `/stop` flip. `model` takes the same short names as `/model`. `elite_effort` and `boss_effort` are the fight efforts (Fight effort, above): a level, `"same"` or `null` for the normal effort, or left out for high-or-the-normal-effort-when-higher; the mod writes them only once `/effort elite` or `/effort boss` sets one. `monthly_budget_usd` is the mod's own cap; 0 means the API is never used. `claude_path` is only needed when Claude Code isn't in one of the usual places (below). `max_tokens` (not shown, normally left out) fixes the API requests' `max_tokens` at a number from 1024 to 128000; without it the brain sizes it from the effort (Request, below). `turn_plan_note` (true or false) and `turn_plan_effort` (a level or null), also not shown and left out unless set, are the turn plan switches for arena measurement (Turn plans, above); a bad value turns the switch off with a line in the log, and the mod saves them only when they are on. There is no key for fast mode: a `fast` key is ignored with a line in the log, since `/fast on` only ever lasts until the game closes (Fast mode, above). Keys the mod doesn't know are kept when it saves, and a value it can't use falls back to its default with a line in the log.

Each copy of the game reads its settings from its own config folder: `~/.config/spiremind` for Mark's copy, `~/.config/spiremind/bot-<port>` for a bot copy (co-op, below), or whatever `SPIREMIND_CONFIG_DIR` names. A bot copy's folder holds its own config.json, transcripts, fights.jsonl and autostart, the config layered over the shared `~/.config/spiremind/config.json`: the shared file is read first, then the copy's own over it. `monthly_budget_usd` in a copy's own file is ignored with a log line, since one cap holds for every copy; set it in the shared file. The API key is the copy's own `api_key`, else the shared `~/.config/spiremind/api_key`, else `ANTHROPIC_API_KEY`; the log says "from api_key" or "from the shared api_key", never the key. A bot copy's `/model`, `/effort`, `/start` and `/stop` save only `model`, `effort`, `elite_effort`, `boss_effort` and `autostart` to its own config.json and never touch the shared one, so `/effort boss max` sent to the bots from Mark's window lasts past the next run start and a relaunch (`/fast on` doesn't: it is never saved, and a relaunched bot copy plays at normal speed). A fight effort set back to `default` is left out of the copy's file, or written there as `"default"` when the shared file sets one.

Spend is tracked in `~/.config/spiremind/spend.json` per calendar month (UTC), from each response's `usage` and the price table in `ModelPrices`. A response that ran in fast mode (its `usage.speed` says `fast`) is priced from the fast table there, at twice the standard rates (Fast mode, above). A model the table doesn't know is priced at the highest of each rate in it, so the estimate errs high. There is no API to read the credit balance with a normal key, so this is the mod's own estimate. Reaching the monthly cap stops the API brain with a chat line, and the subscription takes over. Every copy counts into that one shared spend.json, so the cap holds across all of them (`/budget` then says "this month across every copy"). Each update reads, merges, changes and writes the file under a cross-process lock (`~/.config/spiremind/locks/spend.json.lock`), so two copies adding at once never lose a cost. Before each request a copy also writes an in-flight estimate under its own id ("main", "bot-17773"): its last request's cost, at least $0.05, or for its first request since the game started and the first of a fresh conversation (which writes the whole prompt to the cache) the largest cost so far, at least $0.50. A copy refuses to start a request when the month's total has reached the cap, or, while other copies have requests in flight, when the total plus their estimates and its own would reach it, so three bots near the cap can't each start a request that together goes over it; one of them gets "Monthly API budget nearly reached: ... and the other copies' requests in flight would go over it". A copy alone is refused exactly when the total reaches the cap, as before. The estimate is removed when the cost is added or the request fails unbilled, and one older than 10 minutes no longer counts. If the lock can't be had within 5 s, the copy counts without it and logs once.

### Folders

`BrainPaths` works them out for every brain start, so a `repo` added to config.json applies at the next `/start`. The log shows them when they change.

- **The repo** (the STS2B checkout): `repo` from config.json when that folder has `.claude/commands/play.md`. Otherwise the folder named in the mod's `brain/repo_path`, which `scripts/build.sh` writes with the checkout it built from, when that folder has the play prompt. Otherwise none. So a mod installed with `scripts/install.sh` finds the repo without any config, as long as the checkout stays where it was built.
- **The prompt folder**, which the API brain's system prompt is built from: the repo, else the mod's `brain/` folder, where `scripts/build.sh` stages copies of `play.md` and the `strategy/` notes.
- **The notes root**, which holds the run journal `runs/current.md`, `strategy/learned.md` and the wiki's pages under `strategy/wiki/`: the repo, else the shared `~/.config/spiremind` (also for a bot copy, so the notes stay shared), so the journal survives reinstalling the mod. A `strategy/learned.md` there is preferred over the staged copy when the prompt is built, so lessons accepted there without the repo reach the next run (the pending files sit beside it in `strategy/pending/`). The prompt's wiki index lists the pages there, the ones the notes tools can read, so without the repo the staged wiki isn't used and the brain starts its own.
- **The subscription brain's working folder**: the repo only, since Claude Code needs the real checkout for `/play` and its file tools. Without one it stops with a chat line asking for `repo` in config.json.

## Who plays

`BrainController` (Core) picks the brain and owns the commands. It is built at mod load and lives until the game quits.

- The API brain plays when there is a key, this month's spend is under `monthly_budget_usd` and the API hasn't failed during this run. It may start at the menu, since it idles there for free.
- Otherwise the subscription brain plays, and only while a run is in progress, so it never spends subscription turns at the menu. Once the poll loop has seen the run over (game over or the menu) for 2 minutes, which leaves time for the post-mortem, a subscription brain still playing is stopped without a chat line, and the next run starts it again. A run continued within those 2 minutes keeps it.
- When the API brain stops because the key is missing or rejected, the credit is gone, the Console spend limit or the monthly cap is reached, the chat says "Switching to your Claude subscription for the rest of this run." (or "for the next run", when it happened between runs) and the subscription brain takes over. Whether a run is in progress is what the API brain itself saw last, since a request that fails at once can come between a run start or a game over and the poll's next look. The next run tries the API again: "New run, so back on your API credit."
- It never switches for 429, 529, 5xx or network errors. The API brain retries those itself with a growing pause (30 s doubling up to 5 minutes) and says why once: "Can't reach Claude right now, retrying.", "Claude is overloaded right now, retrying. /model switches models." or, for a 429, "Claude is rate limiting your API key, retrying. /model switches models." with the API's own sentence. A `/model`, `/effort` or `/fast` typed meanwhile goes into the next try. A request that asked for fast mode is the one exception to the waiting: its 429 or 529 sends it again at once at standard speed and switches fast mode off (Fast mode, above).
- A brain that stops with an error, or that something other than the controller stopped, isn't restarted until the next run starts (while autostart is on) or `/start`.
- A subscription brain that stepped back because the run ended (`RunEnded`) is started again once a run is in progress. If it keeps ending while the run goes on, it is restarted at most 3 times per run.
- One brain at a time: a new one starts only after the last one has stopped, or after 15 s, when the old one is aborted. Two brains would cancel each other's `wait_for_decision`.
- A poll loop reads the screen every 5 s from mod load until the game quits, so the controller knows whether a run is in progress even while autostart is off. It acts only while autostart is on. Each run start resets the run's spend and reads config.json and the key again, so a key added meanwhile is used from the next run (or at once, with `/start`).
- Brains announce their own stops in the chat, once. `UserStop` and `RunEnded` are never announced, and the controller only adds the lines about switching.

Command handlers run on Godot's main thread and never wait: brains start on their own tasks, and stopping one happens on a pool thread.

## Co-op

In a co-op run only bot copies play. Mark plays in his own copy, and each bot is a second copy of the game on the same Mac, started with `--sts2bot=1` and its own `SPIREMIND_PORT` (`docs/chat.md`, Co-op, has the relay and the launcher contract).

- **Role.** At mod load `InstanceRole.Detect` reads Godot's `OS.GetCmdlineArgs()`: `--sts2bot=1` (or `--sts2bot 1`, `true`) makes a bot copy; anything else, or no flag, is Mark's copy. A copy that runs with Steam (`SteamInitializer.Initialized`) is Mark's copy whatever its flag says, and so is one where that check throws; both log an error saying the flag was ignored, so a stray `--sts2bot=1` in Steam's launch options can't make his own game play by itself. The log line `role: ...` says which, with its folders.
- **A bot copy** starts its brain by itself (autostart is on for the session without being saved), so it plays as soon as a run is in progress with no `/start`. `/stop` still stops it until `/start` or the next launch.
- **Mark's copy** never plays in a co-op run or lobby (the last snapshot's net type, or the once-a-second look at character select and the run in `Game/InstancePoll.cs`): `/start` answers why, autostart only logs it, and a brain that was playing is stopped with one line at the controller's next poll. The API brain checks the same gate itself before every request and every `act` or `act_sequence`, so one that was idling at the menu sends and plays nothing in the seconds before that poll ("brain: holding back: ..." in the log; an act already asked for comes back "Not run: ..."). In co-op, while bots exist, `/start`, `/stop` and the other brain commands (`/fast` among them) typed in Mark's window go to the bots instead (`docs/chat.md`). Solo play in Mark's copy is unchanged, also while a bot copy from an earlier co-op session is still running: nothing is blocked, and only a command or line that starts with a linked bot's name goes to that bot.
- **Run journal.** A bot copy keeps its own journal, `runs/bot-<port>/current.md` under the notes root, and archives next to it (`runs/bot-17773/2026-10-10-silent.md`). The notes tools still call it `runs/current.md`, so the prompt and the model don't change; the subscription brain's prompt names the bot's journal. Mark's copy keeps `runs/current.md`.
- **Shared notes.** `strategy/learned.md` and the wiki stay shared by every copy. Every notes read, write, append and list takes a cross-process lock (`~/.config/spiremind/locks/notes.lock`); one that can't be had within 5 s gets "The notes are busy (another copy is writing them); try again in a moment." A `notes_write` to learned.md or a wiki page is refused when the file changed since this brain last saw it (in its prompt, or through `notes_read`): the error says another bot copy or a hand edit changed it, carries `changed_since_read: true`, and tells the model to read it again, merge and write, or to use `notes_append`, which never wipes anything. The prompt carries learned.md's whole text but only the wiki's index, so a bot copy must also have read an existing wiki page (or written it) in its current conversation before it replaces it; otherwise the error says it hasn't read the page, carries `not_read: true` and asks for the same read and merge. A fresh conversation (new run, refresh, model change) starts with no page read. A file that doesn't exist yet is always writable. Solo use never meets it: Mark's copy takes the pages in its prompt as read, as before co-op, nothing else writes, and each write updates what was seen.
- **Teammates in a fight.** A teammate plays in the same window as the bot, so `act_sequence` checks before each step what they changed (the numbers its plan rests on, and the game's record of their actions, `team_since`) and stops to re-plan, and an `act` sent on an older snapshot runs only when what teammates changed doesn't touch it (act_sequence, In a co-op fight, below).
- **Repeated waits.** A co-op decision the last `wait_for_decision` already handed over (the bot's map vote is in and Mark's isn't) is held back for up to 60 s, until the snapshot changes or a message arrives. The API brain does this in its own local wait (No idle spending, below); for Claude Code (`/play` or the subscription brain) `BotTools` does the same in the tool itself, for snapshots that list teammates, so each return of the wait is worth a turn. `act`, `act_sequence` and `party_pitch` reset it, so the map vote still waiting after a pitch is handed over at once.
- **Planning sessions.** Bot copies agree on their lanes for the act in short sessions run from Mark's copy (Planning sessions, below).
- **Party chat.** Another bot's line reaches the brain as a chat message with `teammate: true`. It never wakes a waiting or idle brain, so it costs no extra request; it goes to the model with the next tool result, or, when the model had ended its turn and the brain was waiting or idling for it, in a text block ("Earlier lines in the game chat while you waited ...") beside the state that ended the wait.

### Planning sessions

At set points in a co-op run the bots stop for a short planning session, so their decks complement each other instead of chasing the same cards. Mark's copy runs it (`PartyConductor`, owned by the relay); each bot copy takes part through its tools (`PartyBot`, set on `BotTools.Party` at mod load in bot copies only). Nothing goes over the game's network: the steps travel on `POST /coop/party` and the bots' reports on their `/coop/info` and `/chat` polls. `strategy/coop.md` (Planning sessions) tells the model how to take part, and `play.md` points there.

**When.** Each bot copy works out from its own snapshots whether a session is due (`PartyTriggers`) and reports the key under `party.due`:

- `A<act>-start`: an Ancient's event (`state.ancient` true), or the act's map before its first room. The Ancient's pick is the first big build choice of the act.
- `A<act>-mid`: the map once the row reached is at least half the boss row, while more than two rows are left before it.
- `A<act>-boss`: the map from two rows before the boss row, where the next pick is normally the rest site, so Mend and Smith calls come in time. A boss session settles that act's mid one too.
- The boss row is the lowest map row with a boss node, so the second boss is ignored. A bot forgets its settled keys at the menu, at game over and when the act goes down (a new run).
- `/plan` in Mark's window opens a manual session (`A<act>-plan<n>`) at any screen off combat. During a fight it answers "Planning works off combat; try again on the map." `/plan off` stops the automatic ones; `/plan` still works then.

**How a session runs.** The first time a live bot reports a key nobody settled, the conductor waits 3 s for the other bots, then opens it with every live bot that is in the run, playing (API or subscription), not paused and able to plan. Mark's chat gets an opening line, such as "Planning for act 2 (up to 2.5 minutes; the bots hold their Ancient picks). Mark, tell them what you're building, or /plan skip." Then:

- Act start and manual sessions: a lead of 10 s for Mark to say what he builds (his first line ends it), round 1 for every bot at once, a wait of up to 30 s for his answer when a bot asked him something (his first line ends it), then round 2, one bot at a time in port order, each seeing the pitches so far and his lines. Round 2 is only for the bots that pitched in round 1, and it is skipped when fewer than two did and none asked anything.
- Mid and boss sessions: round 1 only.
- A bot has 40 s for its turn; after that the chat says "Silent didn't answer in time; going on.", its round 1 pitch stands, and it isn't asked again in that session. A round 1 pitch that comes in late still goes into the plan. The cap closes the session with whatever came in: 150 s for act start and manual sessions, 75 s for mid and boss. `/plan skip` ends it at once.
- On close the pitches are merged into the party plan (the bots' lanes and takes, what each needs and gives, the party calls, Mark's lines and the questions), the plan goes to every bot with its own section, and the chat gets a summary ("Party plan set: Silent poison (debuffer); Defect frost orbs (protector). Saved in runs/party/plan.md."). The plan is written to `runs/party/plan.md` under the notes root, at most 4 KB (Mark's oldest lines go first, then the oldest questions), with `plan.json` beside it, each through a temp file renamed over the old one. At a new run the old plan is moved to `runs/party/<yyyy-MM-dd-HHmm>.md`. When Mark's copy starts, a saved plan under 3 hours old is taken up again. `runs/party/` is in `.gitignore`. Without a notes root the plan stays in memory.
- `/plan show` lists each bot's lane and the calls.

**Held picks.** While a session is open, a bot copy's pick screens (card reward, rewards, shop, treasure, rest site, event, and a card select off combat) are held until the plan is out, or until the session's time plus 15 s on the bot's own clock. Before a session opens, the act-start Ancient is held for up to 15 s once the conductor has said hello with automatic sessions on, so the Ancient pick waits for the plan. The map, fights, hand selects and the Crystal Sphere are never held. A held screen is shown to the model like a paused one (`awaiting_decision` false, `waiting: "held for the party's planning session"`, no actions), and `act` or `act_sequence` on it is refused with "Held for the party's planning session (A2-start, up to 140 s more): pick after the plan is set. Call wait_for_decision; it returns at your turn to speak or when the plan is out."

**The model's side.** `wait_for_decision` returns early when it is the bot's turn to speak, with the turn brief under `party` (`your_turn: true`, the question in `ask`, the pitches so far in `said`, Mark's lines in `mark`, the plan so far). The model answers with one `party_pitch` call: `say` (its line to the party, spoken like `say`), `role` (debuffer, protector, damage, support or flex), `archetype`, up to 4 short items each in `wants`, `needs`, `gives` and `calls`, and an optional `question` for Mark. `party_pitch` is offered only in a bot copy with `BotTools.Party` set, and outside the bot's turn it is refused with "Not your turn in the planning session; call wait_for_decision." When the session closes, the next result carries the plan once under `party` (`closed`, a `note` telling the model to check its section and update its Build plan, `plan`, `yours`, `calls`). From then on every pick screen carries `party: {yours, calls}`, so the bot checks its part before each card, relic and shop pick. Mark's orders still come first.

**The API brain.** `party_pitch` counts as a tool that moves the game on. After a pitch that went through, the brain runs its local wait at once and puts what came back in the pitch's result as `next` (a decision the turn brief's wait already showed, such as the map vote, is handed over at once, not held as a repeat), so a planning turn costs one request; a `wait_for_decision` in the same reply then returns `{"waited": "Already waited after party_pitch: its result's next is the game now."}`. The local wait also ends on a turn brief it hasn't handed over yet and on the closed-session news. A fresh conversation carries the plan in its first message, under "## Party plan (from the planning sessions)" after the run journal.

## How the API brain works

```
ApiBrain (background task)                      BotTools (same instance the MCP endpoint uses)
  system = play prompt + strategy notes  ──────►  get_state, wait_for_decision, act, act_sequence,
  tools  = BotTools specs + notes tools           say, get_deck, get_persona
                                                  (+ party_pitch: co-op bot copies only)
                                                  (+ notes_read, notes_write, notes_append,
                                                     notes_list: brain only)
  loop: POST /v1/messages ─► tool_use blocks ─► run each tool in-process ─► tool_result ─► repeat
```

- **ClaudeClient** (Core): `POST https://api.anthropic.com/v1/messages` with `x-api-key`, `anthropic-version: 2023-06-01`. No SDK, so the mod stays one DLL. Retries 429 (honouring `retry-after` up to 5 minutes, or up to 30 seconds for a request in fast mode, which the brain would rather send again at standard speed), 529 and 5xx with exponential backoff and jitter, at most 5 tries. Replies aren't streamed, so each try waits 10 minutes, or longer when `max_tokens` could take longer to write (30 minutes at 64000, an hour at 128000), and its connections use TCP keep-alive so a router doesn't drop them while a long reply is written. Classifies errors so the brain can tell the human what happened: out of credit (402, or 400 whose message contains "credit balance is too low"), spend limit (400 "reached your specified API usage limits", or 429 with `enforced_spend_limit_reached`), bad key (401), everything else. The key is redacted from everything it logs or throws.
- **System prompt** (`PromptBuilder`): the play prompt (`.claude/commands/play.md`, with `$ARGUMENTS` read as "the whole run"), then the strategy notes it tells the model to read, included since the brain can't read them itself: `strategy/general.md`, the rules sheet `strategy/rules.md` (labelled as the verified rules for this game version), the boss and elite notes `strategy/bosses-and-elites.md` that general.md points to, the character's file in `strategy/characters/`, `strategy/learned.md`, and `strategy/coop.md` in co-op. Then a Wiki index section: one line per page under the notes root's `strategy/wiki/`, its path and summary, sorted, at most 200 with a last line saying how many more `notes_list` shows, or a line saying the wiki is empty. Page text isn't included; the brain reads a page with `notes_read` when it needs it. A short appendix about this harness comes last: the notes tools, that lessons are held for review and their one-line form, the journal's header line in the exact form `runs/README.md` gives (which the brain can't read), and waiting. Missing files are skipped. It is rebuilt only when a new run starts or the character changes, so the cache holds, and the wiki index stays as it was when the prompt was built (`notes_list` shows pages added since).
- **Request**: model and `output_config.effort` from settings (the effort the conversation started with, a fight room's when it started in one; leaving the room lowers it inside the conversation, Fight effort above); thinking `{"type": "adaptive", "display": "summarized"}` on the models the API docs list with that option (`ModelPrices.SummarizedThinkingModels`: Opus 5.5, Opus 5, Sonnet 5.5 and 5, Haiku 5.5, Fable 5.1 and 5, Mythos 5.1 and 5), and no thinking field on any other model, as before. Opus 4.8 and 4.7 take the option too but are left out on purpose: thinking is off on them unless the request asks for it, so sending the field would make them think and cost more. Thinking is on by default on all the listed ones, and Opus 5.5 can't turn it off, so the field only changes what comes back: each thinking block carries a readable summary of the reasoning instead of an empty string (the default `display` is `"omitted"`). It is billed the same either way. No temperature. `system` is one text block with `cache_control: {type: ephemeral, ttl: "1h"}`, and the request sets top-level automatic caching so the growing conversation is cached too. Tools are sent with `strict: true` and `additionalProperties: false`; constraints strict mode doesn't take (minimum, maximum, maxItems and the like) move into the description and the tool still checks them. `tool_choice` stays auto (any/tool are refused by Opus and Sonnet 5.5). `max_tokens` is 16000 at low and medium effort, 32000 at high and 64000 at xhigh and max (the effort the request is sent at, a fight room's or a turn plan's raise included), since thinking counts toward it and runs longer at the top levels; `max_tokens` in config.json overrides it. It is only a ceiling, billed for what is used. While `/fast` is on and the model takes it, the request also has `"speed": "fast"` and its beta flag (Fast mode, above); off, it has neither.
- **Conversation**: assistant content is kept exactly as received (thinking blocks with their summaries and signatures included) and sent back unmodified. Tool results go back as one user message of `tool_result` blocks, JSON text, `is_error` from the tool.
- **No idle spending**: when the model calls `wait_for_decision`, the brain keeps waiting locally (repeated in-process waits, no API calls) until there is a decision, a chat message, news from a planning session, or the brain is stopped. Menus, enemy turns, teammates and pauses cost nothing. A wait repeated on a decision the last wait already handed over (the human said "hold on" without `/pause`, a co-op ally to wait for) is held for up to 60 s, until the snapshot changes or a message arrives, so it costs a request a minute at most. Nothing is sent at all until a run is in progress or the human writes.
- **Chat**: messages from the human arrive in the tool result's `chat.messages` and again in a text block after the tool results, since Sonnet 5.5 and Haiku 5.5 can take user text inside a tool result for an injection attempt.
- **Refusals**: a reply with `stop_reason` "refusal" (a safety classifier declined) starts one fresh conversation; a second one in a row stops the brain. The category goes to the log and the transcript.
- **Fresh context instead of endless history**: once the conversation passes 60k prompt tokens and the bot reaches the map, or passes 150k anywhere (on Haiku, 20k below its 100k long-prompt tier), the brain starts a new conversation. In a fight (the combat and hand_select screens, and a card choice that opens mid-fight) the 150k refresh waits, so a fresh conversation doesn't cut the fight in half and drop its earlier turns and the pages read: it happens on the first screen after the fight (rewards or game over), or in the fight once the conversation passes 300k (`FightRefreshTokens`). The log says "the fresh conversation waits until the fight is over" once per conversation. This is only for models without a long-prompt tier; Haiku keeps its own limit, and a full context window or a prompt the API calls too long still starts a fresh conversation at once. So does a new run, a changed character, a changed model or effort (not a changed speed: `/fast` keeps the conversation), entering an elite or boss room (and leaving one on a model without per-message effort, Fight effort above), and a prompt the API calls too long. Its first user message holds today's date (local, for the journal's header line), the run journal (`runs/current.md`: Build plan, Orders, floor log), the party plan in a co-op bot copy that has one, the last 10 chat lines, any chat messages the model hasn't seen and the current state, and asks it to carry on. The system prompt and tools are unchanged, so their cache survives (on a model that renders the effort ahead of them, each top-level effort has an entry of its own; Fight effort above).
- **end_turn without a tool call**: the model thinks it is done. If a run is in progress, the brain answers "Keep playing: call wait_for_decision." More than 5 in a row without playing stop the brain, as do more than 2 replies in a row cut off at max_tokens, so a model that won't play can't burn money. Outside a run it idles locally until a run starts or the human writes.
- **Notes tools** (brain only; Claude Code has its own file tools): `notes_read {file}`, `notes_write {file, content}` (the whole file) and `notes_append {file, content}` (a line at the end, for the floor log or a wiki lesson) for `runs/current.md`, `strategy/learned.md` and wiki pages under the notes root. A wiki page is `strategy/wiki/<slug>.md` or `strategy/wiki/<folder>/<slug>.md`, folder and slug lowercase letters and digits with single hyphens between words: no deeper folders, no dots, backslashes or capitals (so never `README.md`; the name `readme` is refused too, since a Mac's disk usually ignores case, and so are the Windows device names such as `con`, `nul` and `com1`). The `file` property is a plain string, since strict tool schemas take neither an enum that could hold pages nor a pattern; the tools check it and list the allowed forms in their error. A write creates the folders it needs. Nothing else is readable or writable. `notes_list {}` returns every page (path, bytes, the title from its first line's heading, the summary from the next non-empty line unless that is a heading) sorted by path, and whether the two fixed files exist. A file may be at most 32 KB, small enough that it always fits in one reply; a write or append past that is refused with a hint to prune old log lines or lessons. Writing `runs/current.md` with a new header line, or without the post-mortem the old journal has, archives the old one as `runs/<date>-<character>.md` first; nothing else is archived. A write that replaces a wiki page with a `## Facts` section is refused unless everything above its `## Lessons` heading is unchanged (line endings, trailing spaces and trailing blank lines aside), so a rewrite to fix a lesson can't alter the verified facts. Lessons are held for review (Lessons wait for review, below): `notes_append` to `strategy/learned.md` or a wiki page puts the line in a pending file instead, and the lesson lines a `notes_write` adds there go the same way.
- **Another client**: if Claude Code's `/play` (or a leftover subscription brain) starts its own `wait_for_decision`, the brain's wait is cancelled and the API brain stops with a chat line instead of fighting over the game.
- **Transcripts**: each conversation is appended to `~/.config/spiremind/transcripts/<date>.jsonl` (requests without the system prompt, responses with usage and cost, and the effort and the speed each request was sent at) for debugging and tuning. An entry whose response has thinking summaries also has a `thinking` list with their text, in order, so a reader can see why a move was made without digging through `content` (which still holds the blocks as received).
- **Fight log**: one line per fight in `fights.jsonl` in the copy's own config folder (`~/.config/spiremind/fights.jsonl`, a bot copy's in `~/.config/spiremind/bot-<port>/`), see Fight log below.

## Subscription fallback

`SubscriptionBrain` lives in Core with everything else: it starts processes through `IProcessLauncher`, which is `ProcessLauncher` (around `System.Diagnostics.Process`) in the mod and a fake in the tests. It runs Claude Code in the repo folder. Mark's Mac has the CLI from Homebrew (v2.1.287 on 2026-10-09). Haiku 5.5 needs Claude Code 2.1.293 or newer: older versions take its full id but report a 200K context and a guessed cost, and read the short name `haiku` as Haiku 4.5 (the brain always passes the full id). Homebrew's `claude-code` cask follows the stable channel and can lag behind; `claude-code@latest` follows the newest release. The arguments, as built:

```
claude -p "/play the whole run" --session-id <uuid> --strict-mcp-config
  --mcp-config '{"mcpServers":{"spiremind":{"type":"http","url":"http://127.0.0.1:<port>/mcp/own"}}}'
  --tools Read,Glob,Edit,Write,ToolSearch --permission-mode dontAsk
  --allowedTools mcp__spiremind "mcp__spiremind__*" "Edit(//<repo>/runs/**)" "Edit(//<repo>/strategy/**)"
  --output-format stream-json --verbose --model <model>
```

A resumed session gets `-p "Keep playing: the run isn't over. Call wait_for_decision."` and `--resume <uuid>` in place of `--session-id`, with every other flag repeated. `--model` is the model from config.json, the same one the API brain uses, read as each session starts, so a `/model` change reaches Claude Code at its next session or resume.

- The binary is found by absolute path, since a game started from Steam has no shell PATH: `claude_path` in config.json, else `/opt/homebrew/bin/claude`, `~/.local/bin/claude`, `/usr/local/bin/claude`, `~/.claude/local/claude`. None found stops it with a chat line saying how to install it.
- Before anything else, `claude auth status` must exit 0 within 15 s and print JSON with `loggedIn` true; otherwise the chat says Claude Code isn't signed in. Its output can hold the account's email, so only `loggedIn`, `authMethod` and `subscriptionType` are logged.
- It waits for a run to be in progress before the first session.
- The child's environment loses `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `CLAUDECODE` (the marker Claude Code leaves for its own children) and every `CLAUDE_CODE_USE_*`, so it bills the subscription login, never the API credit. Its PATH starts with the binary's folder, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin` and `/bin`, for node and helpers. Its standard input is closed at once.
- Its stream-json output is read line by line and logged: `system/init` with the MCP server status, assistant text (cut short), the tools it calls, the result with the names of any tools `dontAsk` refused (`claude: permission denied for ...`; their inputs aren't logged), and stderr.
- A session ends when the process exits. Then, in order: a usage limit message stops the brain with "Your Claude subscription hit its usage limit, so the bot stopped." plus Claude Code's own sentence when it says when the limit resets. A finished run stops it with `RunEnded`, which isn't announced; the controller starts it again with the next run. Three sessions in a row that end within 2 minutes stop it with "Claude Code keeps exiting early". A session Claude Code can't find any more starts afresh with a new id. Anything else is resumed.
- `/stop` asks Claude Code to quit (SIGINT) and kills it after 5 s if it hasn't. The log says how that went: "exited with code N after the stop", plus a line first when SIGINT couldn't be sent and it was killed at once, or "killing Claude Code" when it didn't quit within the 5 s. Quitting the game kills it at once, with every process it started.
- The play prompt is the same `.claude/commands/play.md`, so both brains behave alike. Chat reaches it through the MCP tool results as usual.
- It reads strategy notes and wiki pages with Read and lists the pages with Glob (`strategy/wiki/**/*.md`); both are read-only, so like Read before it, Glob needs no allow rule inside the repo. It writes the journal, new and corrected wiki pages and the pending lesson files in `strategy/pending/` with Edit and Write, which the `strategy/**` rule covers at any depth, new folders included. Nothing stops Claude Code from editing a page's Lessons or reading `strategy/pending/` but `play.md`, which says not to.

## Rules sheet and wiki

`strategy/rules.md` holds the verified combat rules for this game version. Both brains read it with the other strategy notes: Claude Code because `play.md` says to, the API brain in its system prompt right after `strategy/general.md`.

`strategy/wiki/` holds a page per enemy, encounter, card group or other topic, such as `enemies/<slug>.md`, `encounters/act1-overgrowth.md`, `cards/ironclad.md` or `potions.md`; `README.md` there has the conventions for humans. Every page starts with `# <Name>` and a one-sentence summary on line 2, which the index and `notes_list` show, then `## Facts (game files, v0.107.1)`, which the bot never edits, and `## Lessons`, always the last section, so a line appended to a page lands there. Pages the bot makes for topics without one go in `strategy/wiki/lessons/`. `strategy/learned.md` stays the short list of general rules that is always loaded.

`play.md` says when to use it: read a page before the decision it covers (an elite, a boss, an unfamiliar enemy, an event, a card, relic or potion pick), not every turn; write one lesson line after a fight or event that taught something concrete; remove a wrong lesson and hold the corrected one instead of contradicting it; and at the end of a run hold any lesson the run taught that isn't on its page yet and any short general rule for `strategy/learned.md`. The API brain does this with the notes tools and finds pages in its prompt's index; Claude Code does it with Read, Glob, Edit and Write.

### Lessons wait for review

Every lesson has one form, one line: `- (Character, YYYY-MM-DD, <source>) <lesson>`, where the source is a fight id from the fight log (`2026-10-11 A1 F7`: the date, act and floor) or the floor (`floor 7`). For example `- (Ironclad, 2026-10-11, 2026-10-11 A1 F3) Chomp hit for 11 on turn 1; Defend first.`

A lesson the bot writes doesn't go on the page. It goes to a pending file in `strategy/pending/` under the notes root, at the page's path below `strategy/`: `strategy/pending/wiki/enemies/jaw-worm.md` for `strategy/wiki/enemies/jaw-worm.md`, and `strategy/pending/learned.md` for `strategy/learned.md`. A new pending file starts with `# Held for review: <the file it is for>`, and a line already there isn't added again. The folder is outside the wiki and its files aren't notes files, so the system prompt, the wiki index, `notes_read` and `notes_list` never load them, and a held lesson can't steer a later fight. Only lesson lines are held, though (below). Once a lesson has been checked, Mark moves it under the page's `## Lessons` (or into `learned.md`) by hand.

In the game (`NotesOptions.HoldLessons`, on by default):

- `notes_append` to `strategy/learned.md` or a wiki page (it would land under Lessons, the page's last section) must be one lesson line in that form, or it is refused with the form and an example, and nothing is written. A good one goes to the pending file and the page is left alone. The tool result says `"held_for_review": true` and that the lesson was saved for review and won't show in `notes_read` or the prompt, so the bot doesn't add it again.
- `notes_write` to `strategy/learned.md` or a wiki page writes everything but the lines it adds below the page's `## Lessons` heading (for `learned.md`, anywhere but headings); those go to the pending file and the result lists them under `held_for_review`. A line counts as added when the old file has no such line, so reordering adds nothing, and removing a lesson works at once. If an added line isn't in the lesson form, the write is refused and nothing is written. The Facts check comes first. Everything else the write adds goes on the page at once: a new page's summary line and other sections, or a section above `## Lessons` on a page without Facts. Those show in the wiki index and `notes_read` straight away, so a page the bot starts is worth a look. A wiki write without a `## Lessons` heading is refused, so leaving the heading out can't put new lines on the page untested.
- The run journals (`runs/current.md` and a bot copy's `runs/bot-<port>/current.md`), with their Build plan, Orders and floor log, are written as before.
- The co-op guard is unchanged: a held append leaves the page as it was, so it needs no read and doesn't make another copy's read stale, while a bot copy must still read a page before it replaces it, and a write after another copy's change is still refused. A write's held lines aren't on disk, so the guard takes the written text as seen.
- A pending file can hold 32 KB like any notes file; past that the bot is told to keep the lesson in its journal until someone reviews the file.

## Fight log

`FightLog` (Core) writes one JSON line per fight to `fights.jsonl` in the copy's own config folder, next to its `transcripts/` (`~/.config/spiremind/` for Mark's copy, `~/.config/spiremind/bot-<port>/` for a bot copy, so each copy keeps its own). It is fed from what the API brain already sees: every snapshot in a tool result, and its own requests. The subscription brain doesn't feed it. A fight opens at the first combat or hand_select snapshot with the whole board and closes at the first snapshot of another room's screen (rewards, card reward, map, shop, rest, event, treasure, game over, the menu); a card choice mid-fight, a modal, an unknown or error screen and busy snapshots keep it open. A board from another floor closes a fight that was never seen to end. A fight line:

```json
{"at": "2026-10-11T14:03:12.0000000Z", "kind": "fight", "id": "2026-10-11 A1 F5", "character": "The Ironclad",
 "act": 1, "floor": 5, "room": "Monster", "enemies": ["Leaf Slime (S)", "Twig Slime (M)"],
 "result": "won", "ended_on": "rewards", "hp_before": 80, "max_hp_before": 80, "hp_after": 66, "max_hp_after": 80,
 "turns": 3, "seen_from_turn": 1, "potions_used": ["Fire Potion"], "potions_discarded": [], "potions_held": ["Blood Potion"],
 "effort": ["medium"], "speed": ["standard"], "requests": 4, "refreshes": 0, "conversations": 0, "cut_offs": 0, "spent_usd": 0.22,
 "started_at": "2026-10-11T14:01:40.0000000Z"}
```

- `id` is the player's local date, the act and the floor: the source a lesson quotes. `enemies` lists every enemy seen in the fight, summons included, by index.
- `hp_after` is from the screen after the fight, so the rewards screen's HP after Burning Blood's heal; `potions_held` is that screen's potions too. On game over, `result` follows what the game over screen says: `won` for a victory, `lost` for a defeat, `abandoned` for a run abandoned from the pause menu, and otherwise `lost` at 0 HP and `unknown` above it. On any other screen it is `lost` at 0 HP, `unknown` when the fight was never seen to end (it closed on the menu or on a board from another floor), else `won`. `seen_from_turn` above 1 means the brain started mid-fight, so `hp_before` is from then.
- `potions_used` and `potions_discarded` come from the `potion:` and `discard_potion:` ids in the brain's `act` and `act_sequence` results, named from the board they were picked on.
- `effort` lists the efforts the fight's requests were sent at, in order (`default` when none was set), and `speed` their speeds the same way (`standard`, and `fast` while `/fast` was on). `requests`, `cut_offs` (max_tokens replies) and `spent_usd` count the responses that came back during the fight. `refreshes` counts fresh conversations started to save tokens (a long conversation, a full context window, a refusal); `conversations` counts every fresh conversation in the fight, a fight room's effort change included.

At a rest site on floor 16 (the rest before the Act 1 boss) it also writes one deck line, once per run: `{"kind": "deck", "id", "character", "act", "floor", "hp", "max_hp", "gold", "deck_size", "deck", "relics", "potions"}`. A lower floor afterwards means a new run, whose floor 16 rest gets its own.

Nothing in it throws into the brain: a snapshot it can't read or a line it can't write is logged once (until a write works again) and play goes on.

## Wiring and game exit

`BrainWiring` (game side) builds it all once the bridge has started: the settings, the spend tracker and transcript, and the controller with a factory per brain. The API brain gets the same `BotTools` instance the MCP endpoint uses, and learns whether the run is co-op from the last snapshot the bridge took; the subscription brain gets the bridge's port. Both read the screen through `DecisionWaiter.PeekAsync`, which waits for the main thread and never blocks it, and leaves the snapshot version alone: a deck view opened and closed while the model plans would otherwise count as two changes and get its next `act` refused as stale. It uses only Core, System and Godot types, and a failure anywhere only loses the brain, never the bridge or the chat. The mod's folder comes from the DLL's location.

So that a Claude Code child never outlives the game, the scene tree root's `TreeExiting` signal and `AppDomain.ProcessExit` both call `BrainController.Shutdown()`, which aborts every brain: the API request in flight is cancelled and Claude Code is killed with its whole process tree. Only the first of the two does anything. A game that crashes or is force-quit gets no such chance; Claude Code then loses its MCP server and may linger until it notices.

## act_sequence

Both brains get `act_sequence {version, actions: [id, ...]}` to play several actions from one snapshot, typically a whole turn. Ids are from the snapshot named by `version`. The first runs as `act` does. Before each later step, the tool finds the action again in the current snapshot:

- An id with no index or target (`confirm`, `end_turn`, `proceed`) is taken as it is while it is still offered, since a label can carry a count that moves on ("Confirm selection (1 chosen)").
- Any other id is found by its label in the original snapshot, so shifting hand indices don't matter. A play label names only the card, so a cheaper, enchanted or otherwise changed copy looks like the plain one. When several actions share the label, the tool prefers the card whose hand entry (name, cost, enchantment, text) equals the original's, then one that equals it without the text (a Strength gain rewrites every attack's text), then the same id, then the first.

A card that asks for cards from the hand (Armaments, True Grit+, Burning Pact) opens `hand_select` in the middle of the turn. In a sequence that starts in combat, its picks can follow it: `select:<i>` with `i` the card's hand index in the original snapshot (the only one the model has seen), then `confirm`, then the rest of the turn. These picks are not offered in the original snapshot, so the up-front check only makes sure each `select:<i>` names a card in its hand; they are checked when the choice opens:

- `select:<i>` runs as the select, among those the choice offers, for a card of the same name, preferring the one whose hand entry equals the original's, as for plays. The played card has left the hand and picked cards are not offered again, so positions shift. A card that is gone, already picked or not allowed in this choice stops the sequence, and nothing runs in its place. So does a `select:<i>` naming a card the sequence already played or picked, even when a copy with the same name is still in hand (Armaments, Armaments, Bash with `play:0, select:0` stops rather than upgrade the second Armaments).
- `confirm` runs while the choice offers it. When the choice already closed by itself (enough cards picked), it is listed under `not_needed` and the sequence goes on.
- With exactly 1 valid card the game takes it with no prompt (strategy/wiki/cards/ironclad.md), so no choice opens and a planned pick stops the sequence; the stop says the game may have taken the only card itself. The tool description and play.md tell the model to leave the picks out then. The tool doesn't try to tell this from a wrong plan.
- The next play, potion or `end_turn` runs only once the screen is back on combat; a choice still open then stops the sequence as before. A pick with no hand choice open stops it too.
- After an upgrade pick (`state.selection.mode` is `upgrade`, as for Armaments), a later play of that same card (by its original index) is found only under its upgraded name, "Play Bash+ on Jaw Worm" for "Play Bash on Jaw Worm", at the same target, so a plain copy is never played in its place.

A pick from a pile or a choose-a-card screen (Headbutt, the card potions) is `card_select`, whose cards the original snapshot doesn't show, so a `card:<n>` or `bundle:<n>` after a play in combat is refused up front and the sequence stops when that screen opens.

It stops early, returning what it did and the current snapshot, when:

- nothing changed after the last step, or the game refused an action,
- the screen is no longer the one the sequence started on (a choice nobody planned picks for, a pick from a pile, the fight ended), except for the hand choice described above,
- the game doesn't settle into a decision,
- the turn ended (`state.turn` or `state.round` changed), say after a card like Void Form. The settle wait runs through the enemy turn, so without this check the rest of the plan would run on the next hand,
- the bot is paused or a chat message arrives,
- the next label is no longer offered, or a planned pick isn't offered in the choice that opened.

A target's label has " (e1)" after the enemy's name only while another living enemy shares it, so when a twin dies the tool also accepts the action at the same target whose label matches once that tag is dropped. Before anything runs, every id must be legal in the snapshot (picks for a hand choice as above), `end_turn` may only be the last id, the version must match and the game must be waiting on the bot; otherwise it is refused like `act`, and nothing runs. It takes 1 to 12 ids, picks included. The result lists what ran, the confirms that weren't needed, then why it stopped and which ids didn't run, then the snapshot: `{"done": [{"id", "label"}, ...], "not_needed", "stopped", "not_run", "warning", "next"}`, with `not_needed` only when a confirm was skipped and `stopped` and `not_run` only when it stopped early. It is an error only when nothing ran.

The model is told (tool description and `play.md`) to end a sequence after any card or potion that draws, discovers, creates or transforms cards, has a random result it needs to see, opens a pick from a pile or ends its turn, so it sees what it got before planning further (a card that asks for hand cards and then draws, like Burning Pact, ends it after its picks), and to leave out `end_turn` after a card that ends the turn. The tool can't tell those cards apart, so these stops are the model's to make.

### In a co-op fight

A teammate plays in the same window as the bot, so a turn planned from one snapshot can go stale two cards in: Mark gives the bot Block and it plays its Defends anyway. In a `combat` or `hand_select` snapshot whose state lists teammates (a non-empty `team`, or `teammates` when the team couldn't be read), `act_sequence` and `act` check for that (`BotTools.Teammates.cs`). A solo fight skips all of it, so its path is unchanged.

Before each step after the first, `act_sequence` makes two checks:

1. It compares the snapshots before and after the previous step against what that step's card says it does. What the card can't explain is a teammate's.
2. It captures the game again, waiting first if a teammate's card is still resolving. Anything that changed since the step settled is a teammate's. If the game is still busy, the screen changed or the turn ended, it stops for that reason instead. Since that wait can take a few seconds, it then looks again for `/stop`, a pause and a new chat message, as before the step.

What it watches: the bot's Block, energy, HP and powers; each planned target's HP, Block and powers; which enemies are still there; and `incoming_damage`. How it decides what the bot's own card explains:

- **Block**: a gain up to the numbers in the card's "N Block" text, plus the amount of any of the bot's powers whose text mentions Block (After Image). A card that mentions Block with no number explains any gain.
- **Energy**: the card's cost is spent, so a rise above "before minus cost" is a teammate's, unless the card or one of the bot's powers mentions (E) or energy.
- **HP**: a gain is the bot's own only if the card mentions heal or HP.
- **Powers**: a new or bigger buff is the bot's own if the card is a Power or names it, or another of its powers names it. Debuffs, and powers that react to plays (text with "when" or "every"), are left out.
- **Enemies**: an attack, an aimed card, or text with "damage" or "enem" may touch enemies; an aimed card touches its target, and others too when its text says "enemies" or "random". Once the card kills one enemy, others leaving at the same time count as the bot's too (minions that flee). `incoming_damage` moving is left alone after a card that touches enemies or the bot's powers.
- **Potions** explain everything. A `select` or `confirm` is judged by the card that opened the choice, but spends no energy: the card was paid for when it was played.

On a teammate's change it stops and returns `next` with a reason such as `A teammate acted: your Block 0 -> 11. Plan the rest of your turn from next.`; several changes are joined with "; " (`Jaw Worm (e0) is gone; incoming damage 12 -> 0`).

**The game's record.** A co-op fight snapshot can also carry `state.team_since`, short lines on what the others did since the bot's last action, and `state.team_changed` when a line touched the bot, its pet or an enemy (`docs/coop.md`, What the others just did). Both snapshots the checks above look at (the one after the step, and the fresh capture) are read for these too: when `team_changed` is set and `team_since` has a line the model hasn't seen, the sequence stops and names those lines, `A teammate acted: Mark played Lift on you: +11 Block. Plan the rest of your turn from next.` (several joined with "; "). When the numbers moved as well, the lines are given instead of them. Notes:

- Seen means in the snapshot the sequence started from (with an older version, also in the capture its first step ran on), and after that in the last snapshot a check passed. A line stays in every snapshot until the bot's own action clears it, so a line judged once is not judged again.
- Lines are matched one for one by their exact text. The `(N earlier lines left out)` line is skipped, and its count tells which seen lines slid out of view, so a new line that reads like one of them is still new. A line with the same text as one the model planned with, coming after the first step cleared that one, is taken for it; the numbers still catch what it did to the bot or a planned target.
- New lines without `team_changed` never stop it: a teammate blocking for themselves is not the bot's business.
- `team_changed` covers every enemy, so a teammate's hit on an enemy the plan leaves alone stops the sequence too, though the numbers alone would let it run.
- The flag is for all lines together, so it counts for the new lines only when no seen line can have set it: the seen snapshot had no flag, or, at the check after the first step, none of its lines is left (none matches, none slid out of view). Otherwise only the numbers decide. Only the bot's own action clears lines, so a flagged line seen later in a sequence keeps the flag set to the end of it.

**An older version.** Every co-op fight snapshot handed to the model is remembered (the last 16). An `act` or `act_sequence` sent with the version of one of them, after only teammates moved the game on, runs from that snapshot as long as the bot has done nothing since, it is the same turn and screen with the same hand selection, the hand is the same (by name, cost and type), and none of the watched numbers moved for the ids sent, and the record shows nothing new that touched anything. Each id is then found again in the current snapshot by its label, like a later step of a sequence. Otherwise it is refused and says why, checked in this order: `A teammate acted since that snapshot: your hand changed. Nothing was done; plan from the current snapshot.` (Huddle Up); the `team_since` lines the older snapshot lacks, when the current one has `team_changed` and the older one didn't (with it, the older snapshot's own lines may be what sets it: "Mark ended their turn" after a Lift the model saw is no reason to refuse) (`A teammate acted since that snapshot: Mark played Lift on you: +11 Block. Nothing was done; ...`); what moved (`A teammate acted since that snapshot: your Block 0 -> 11. Nothing was done; ...`). A version from before the bot's own last action is never accepted. Off a fight, or in solo play, a stale version is refused as before.

`strategy/coop.md` (Your turn with a teammate) tells the model to keep sequences short while teammates haven't ended their turn, to decide Block last from a fresh snapshot, and to re-plan when a sequence stops this way.

`act` and `act_sequence` both require `version`. An `act` without one is refused before anything runs (`version is required: pass the version of the snapshot your ids came from, ...`), since a second `act` sent in the same reply as the first would otherwise run unchecked on whatever the first led to (item 10 of `docs/opus-review.md`). A version sent as a string or a fraction is refused too, with `version must be the integer snapshot.version; you sent ...`, so the model isn't told it sent none.

## Smoke test

`scripts/dev-host.sh --brain` proves the real API calls work before the first in-game `/start`, with no game running. The real `ApiBrain` plays the dev host's fake fight (one Jaw Worm, the same `FakeGame` the tests use) through the real `BotTools` and chat, with the key from `~/.config/spiremind/api_key`, the effort from config.json and the real spend tracker, so what it costs counts in `/budget`. Three things differ from the game:

- The model is `--model <name>` for this run only (default haiku, to keep it cheap; config.json isn't changed). `scripts/dev-host.sh --brain --model sonnet` tries another.
- The notes and the transcript go to a fresh temp folder, never the repo's `runs/` or `strategy/`, so the live run journal isn't touched. The system prompt is still built from the repo's play prompt and strategy notes, but its wiki index lists the temp folder's pages, so it says the wiki is empty.
- At most `--max-requests` requests are sent (default 6, at most 50). The next one is refused, which stops the brain.

`--fast` (with `--model opus`; another model is refused, since it wouldn't take it) asks for fast mode as `/fast on` does in game, for this run only: `scripts/dev-host.sh --brain --model opus --fast --max-requests 3`. Each response's line then shows the speed its usage reports ("#1 claude-opus-5-5, tool_use, speed fast: ...") and its fast price, and the run passes only when every response ran fast ("Fast mode: all 3 responses say they ran fast."). On a key without fast mode the first request fails, the chat line says Claude turned it down, the fight goes on at standard speed and the run ends with FAILED, which is the answer the test is for. It is the cheapest way to find out before a game depends on it: on Opus 5.5 mostly the one write of the prompt to the cache at the fast price, an estimated 50 cents for about 30k tokens.

It prints each request's model, stop reason, tool calls, tokens (fresh input, cache reads, cache writes with their 1 hour part, output) and cost, then the totals and this month's spend. It ends with PASSED (exit code 0) when the brain stopped at the cap or because it won the fight, and FAILED (exit code 1) when it stopped for any other reason, a request failed, nothing came back, or Ctrl+C or a 10 minute limit cut it short.

What to expect on haiku: a few requests (usually the persona and notes first, then a turn or two of the fight), a cache write of the whole prompt (the system text and tools, over 10k tokens) on the first, cache reads of about that much on every one after, and about a cent in all. No 400s. If the second request reads 0 cached tokens, the start of the prompt is changing between requests, which would cost real money in the game; the script prints a warning for it. A 400 prints the API's own message and means the request (tools, caching, effort) needs fixing before `/start`. The transcript in the temp folder has every exchange.

## Cost

Per decision on Opus 5.5 (input $4, cache read $0.20, output $20 per million tokens): about 30k cached tokens plus 2k fresh plus 500 to 1500 output, roughly $0.02 to $0.04. With `act_sequence` a fight turn is usually one decision, so a full run should be on the order of 200 decisions. With `/fast on` every one of those rates doubles (input $8, cache read $0.40, output $40), so a decision is roughly $0.04 to $0.08.

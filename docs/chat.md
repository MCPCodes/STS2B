# In-game chat

Mark talks to the bot from inside the game, and the bot answers as the character it plays: in a chat box, and in the game's own speech bubbles over its character. The game types, members and behaviours this builds on are in `docs/chat-and-persona.md`.

## What the player sees

- Press **T** (override with `SPIREMIND_CHAT_KEY`, a Godot `Key` name; Enter and Escape fall back to T, since they close the box) to open a chat box at the bottom left. Enter sends and closes the box; Escape closes it; clicking away closes it and keeps what you typed for next time. While the box is open the game's own hotkeys stay quiet, so typing doesn't set them off. A key the game uses itself never opens the box (a game hotkey rebound to it, F2, the dev console toggles `` ` `` `'` `*` `^`, and V in co-op, where it is the emote wheel); the log says so once. The box also stays closed in controller mode, under the Steam overlay and while the dev console is showing.
- A small log above the box shows the last few lines: `Mark: Ironclad, go for Strength` and `Ironclad: Aye. Inflame it is, then.`, the bot's name in its character's colour. When the box is closed, lines fade after a few seconds.
- The bot's lines also appear as a speech bubble in the character's bubble colour: over its character in a fight, beside its figure or the top-bar portrait elsewhere (details under Speech bubbles). A long line becomes a few bubbles in a row. Off combat the bot pauses a moment after speaking before it moves, so the line can be read before the screen changes.
- While the bot is deciding in combat, a thought cloud shows over its character after a couple of seconds and goes away when it acts or speaks.
- The bot answers to its character's name: "Ironclad, ...", "hey Silent", "@Defect". With one bot, an unaddressed message goes to it too. A message that starts with a different character's name is for another bot and is ignored. At character select the bot answers to the character just picked, so "Silent, go poison this run" reaches it once Silent is picked. With nothing picked or Random, and on the other menus, it has no name and every message goes to it.
- Commands, handled by the mod at once without waiting for the model. A message is a command when its first word is `/name`, in any case; the rest of the message is its argument. Commands never reach the model, and an unknown one gets a line pointing at `/help`.
  - `/pause` holds the bot. It finishes nothing new: `act` is refused and `wait_for_decision` holds. The human plays by hand meanwhile. Chat still works. Anything after `/pause` is ignored, so "/pause I'll take this fight" works.
  - `/resume` hands control back.
  - `/start`, `/stop`, `/budget`, `/model [name]` and `/effort [level]` drive the in-game brain (`docs/brain.md`): who plays, on which credit, with which model.
  - `/fast` says whether the API's fast mode is on and what it costs; `/fast on` and `/fast off` switch it. On, the API brain's answers come up to 2.5 times faster at twice the price. It is off whenever the game starts and is never saved (`docs/brain.md`, Fast mode).
  - `/help` lists every command in the log, with its arguments.
- In co-op, Mark talks to every bot copy from his own window: his lines and the brain commands reach them, and their lines come back into his log and as bubbles over their players, with a thought cloud over a bot while it decides (Co-op, below). `/bots`, `/bot add [character]`, `/bot stop [name]`, `/party [on|off]` and `/plan [skip|show|on|off]` are added there.

## Flow

```
ChatOverlay (main thread, stock Godot nodes) ── each bot line ──▶ SpeechBubbles (main thread, every frame)
   │ PostFromHuman("Mark", text)          ▲ LineAdded event          • bubbles over the bot's character
   ▼                                      │ (any thread → queued     • thought cloud from ThinkingSince
ChatHub (SpireMind.Core, thread-safe) ────┘  for the next tick)
   │ unread messages, paused flag, bot name, persona, thinking-since, line log
   │ ◀── BotName, Persona from Identity (main thread, once a second)
   ▼
BotTools (HTTP worker threads)
   • every tool result carries "chat": {...} when there are unread messages or the bot is paused
   • wait_for_decision returns early when a message arrives; a newer one cancels it
   • say(text): the bot speaks; the line goes to the log, the overlay and a speech bubble
   • get_persona: the character as the game describes it
   • act is refused while paused
   • results that hand over a decision set ThinkingSince; acting clears it
```

ModEntry wires it on the `SceneTree.ProcessFrame` tick: `Identity.Poll`, then the overlay's `Tick`, then `SpeechBubbles.Tick`. Each fails on its own and logs once.

### ChatHub (src/SpireMind.Core/ChatHub.cs)

Game-agnostic and unit tested. All members are safe to call from any thread.

- `string? BotName`: the character this bot plays, without a leading "The " ("Ironclad"). The game side (`Identity`) keeps it current: the character in a run, the one picked at character select, null anywhere else. While it is null every message is for this bot.
- `IReadOnlyList<string> KnownNames`: every character name, for telling "a message for another bot" apart from an unaddressed one. Defaults to Ironclad, Silent, Defect, Regent, Necrobinder.
- `JsonObject? Persona`: the character as the game describes it, for `get_persona` (shape below). `Identity` replaces it whole when the character changes and sets it to null with the name. Both the setter and the getter deep-copy, so neither side can change the other's.
- `DateTime? ThinkingSince`: when (UTC) the bot was handed a decision it hasn't acted on yet, or null. `MarkThinking(bool)` sets it (keeping an earlier time) or clears it; BotTools calls it, and `/pause` clears it too, as does the brain controller when a brain stops (`/stop`, or the brain stopping by itself). A mark older than `ThinkingStaleAfter` (5 minutes, above the longest `wait_for_decision`) reads as null and is restarted by the next `MarkThinking(true)`: a session that ended mid-decision leaves no tool call to clear it. The thought cloud reads it.
- `PostResult PostFromHuman(string from, string text)`: trims; a message whose first word is `/name` (any case) is a command and gets a system line instead of a human one: `/pause`, `/resume` and `/help` are built in and change state under the lock (anything after them is ignored), added commands run their handler, and an unknown `/name` gets "There's no /name command. Type /help to see them." A lone "/" or a slash before a space is ordinary text. Anything else logs the human line and, when it is for this bot, queues it as unread. Returns what happened (command handled with its reply, queued, ignored as addressed elsewhere, rejected as empty).
- `void AddCommand(string name, string usage, string help, Func<string, string, string> handler)`: adds a command, or replaces the one with that name. The name is the word after the slash, matched in any case; the built-in names are refused. `usage` is the argument hint `/help` shows after the name (`[opus|sonnet|haiku|fable]`, or empty) and `help` a short phrase ("shows or switches the model"). The handler gets who typed it and the rest of the message, trimmed, and returns the system line (empty for none). It runs on the posting thread, often Godot's main thread, with the hub's lock released, so it may use the hub but must return quickly and never wait for the main thread. A handler that throws gets the line "That didn't work: <message>" instead of breaking the post. `BrainController` adds `/start`, `/stop`, `/budget`, `/model` and `/effort` this way.
- `ChatLine Announce(string text)`: a system line from the mod itself, such as the brain's "Switching to your Claude subscription for the rest of this run." Whitespace collapsed, no length cap or burst limit. Throws `ArgumentException` on empty text.
- `ChatLine Say(string text)`: the bot speaks. Whitespace collapsed, capped at `MaxSayLength` (280) with "..." when cut. Throws `ArgumentException` on empty text. A burst limit (more than 6 lines in 10 seconds) throws `InvalidOperationException` so the model slows down. Each line sets a speech hold of `SpeechHold(text)`: 0.5 s plus 0.05 s per character that isn't whitespace, between 1.5 and 3 s, on the hub's clock. A shorter line never cuts a longer hold short.
- `TimeSpan SpeechHoldLeft()`: what is left of the hold, or zero. BotTools waits it out before acting off combat (below).
- `IReadOnlyList<ChatMessage> TakeUnread()`: hands over and clears the unread human messages addressed to this bot. `bool HasUnread`. `PeekUnread()` returns them without clearing, for the curl debugging routes.
- `bool Paused`, `string? PausedBy`.
- `IReadOnlyList<ChatLine> LinesSince(long seq)`: the log after a sequence number (capped at the last 200 lines). Each `ChatLine` has `Seq`, `Kind` (Human, Bot, System), `From`, `Text`, `At`.
- `event Action<ChatLine>? LineAdded`: raised after the lock is released, on whatever thread caused it.
- For co-op (all additive): `ChatLine.Remote` marks a line that came from another copy through the relay, and the overlay draws no local bubble for it. `ChatMessage.Teammate` marks another bot's line relayed in. `PostResult.Seq` is the line a post logged. `PostFromTeammate(from, text)` logs another bot's line as a Remote bot line and queues it as a teammate message (never a command, no burst limit, no speech hold); teammate messages don't count for `HasUnread`, so they never end a wait early, and at most 20 wait. `AddRemoteSay(from, text)` shows a bot copy's line in the human's log without queuing it. `AnnounceFrom(who, text)` shows a bot copy's system line labelled "Silent: ...". `CommandFilter` sees every command before it runs here (null runs it here, "" ends it with no line, other text is the reply). `HelpNote` is a sentence added to the end of `/help`. `RemoveCommand(name, handler?)` takes an added command back off.
- Addressing: a message is addressed to a name when it starts with that name (or "The name"), optionally after "hey", "hi", "ok" or "@", followed by a comma, colon, space, "!" or "?" or the end. Case-insensitive.

### Tool results

`get_state` and `wait_for_decision` return the snapshot JSON; `act` returns `{done, next}`; errors return `{error, current}`. Each of these gets one extra top-level key when it matters:

```json
"chat": {
  "you_are": "Ironclad",
  "paused": true,
  "messages": [{ "from": "Mark", "text": "Ironclad, go for Strength", "seconds_ago": 3 }]
}
```

`paused` only when true, `messages` only when there are any. Messages are taken (marked read) when the result is built, right before it is returned. A cancelled call never builds its result, so its messages stay unread for the next one. The snapshot version is computed from the snapshot alone, so chat never changes it.

A tool call can outlive its client: Esc in Claude Code drops the request, but the server-side wait would run on and take the next message for an answer nobody reads. Two things stop that. `McpEndpoint` cancels a call when the client sends `notifications/cancelled` for its id (answering the dropped request with JSON-RPC error -32800). And only one `wait_for_decision` runs at a time: a new one cancels the one before.

- `wait_for_decision` returns as soon as an unread message arrives, with whatever the game shows at that moment (possibly `awaiting_decision: false`). While paused it never reports a decision: it waits for a message or the timeout, then returns the snapshot with `awaiting_decision` forced to false, `waiting: "paused by Mark"` and no actions.
- `act` and `act_sequence` while paused are rejected: "Paused by Mark. Call wait_for_decision; you can still talk with say." A pause or an unread message for the bot also ends an `act_sequence` before its next step.
- `get_state` while paused shows the real state but with `awaiting_decision` false and no actions, same as above, so the model doesn't plan moves it can't make.
- `say {text}` returns `{"said": "<text as shown>"}` (plus `chat` when there are new messages). Errors from ChatHub become tool errors. The tool description tells the model where its lines show (over its character in fights and on the rewards after one, beside its figure or top-bar portrait elsewhere) and that a bubble holds about 100 characters.
- The model usually calls `say` and `act` in the same reply, and they run back to back. Outside a fight the move changes the room, so `act` and `act_sequence` first wait out `ChatHub.SpeechHoldLeft()` when the snapshot's screen is anything but `combat` or `hand_select` (in a fight the bubble sits over the character and stays through the move). The wait comes after the up-front checks pass and before the first action runs, once per call. Then the game is read and checked again, so a snapshot that changed during the wait, or a pause, is refused like any stale id. The wait uses the call's cancellation token and runs on the caller's thread (an HTTP worker or the brain's task), never Godot's main thread.
- `get_deck` returns the run's full deck with card text, relics with text, potions, HP and gold, for build decisions. It goes through `IGameBridge.DescribeDeckAsync`.
- `get_persona` returns `ChatHub.Persona`, or the error `"no character yet; call get_persona again once the run has started"`, with the usual `chat` key. The play prompt calls it once at the start and after context compaction, and again once the run has started if it had no character yet or the character changed.

Thinking, for the thought cloud: when `get_state` or `wait_for_decision` hands back a snapshot with `awaiting_decision` true and actions, or `act` or `act_sequence` hands back one (its `next`, or the `current` it was refused against), BotTools calls `MarkThinking(true)`; any other result of those four clears it. `act` and `act_sequence` clear it as soon as they start. Paused snapshots never await a decision, so they clear it. `say`, `get_deck` and `get_persona` leave it alone, since the model calls them mid-decision.

### HTTP

- `POST /chat` `{"from": "Mark", "text": "...", "teammate": false}` posts as the overlay does (curl testing, and the co-op relay). With `"teammate": true` it is another bot's line relayed in (`PostFromTeammate`). It answers `{"outcome": "queued" | "command" | "not_for_me" | "empty", "reply": ..., "seq": ...}`, with 400 for empty text; `seq` is the line it logged, or null. A body that isn't JSON gets 400 `{"error": "body must be a JSON object: ..."}`, here and on `/act`.
- `GET /chat?since=<seq>` returns `{"bot": "Ironclad", "paused": false, "lines": [...]}` plus who this copy is: `role` ("bot" or "human"), `port`, `instance` ("bot-17773" or "main"), `session` (new every launch), `net_id` (null until known), `character`, `playing` ("api", "subscription", "none" or null) and `last_seq`. Each line has `seq`, `kind` (human, bot, system), `from`, `text`, `at` and `remote`.
- `GET /coop/info` returns the same identity fields with `name`, `version` and `paused`, for the relay's discovery.
- Both also carry `thinking` (true while `ChatHub.ThinkingSince` is set, so the relay can draw the bot's thought cloud), and a bot copy adds `status`: `{"line", "character", "in_run", "join_stopped"}`, where it stands in the lobby (Co-op, below). A bot copy that can plan with the party adds `party`, its report for the planning sessions (`docs/brain.md`, Planning sessions).
- Three routes take the relay's requests, in bot copies only (403 `{"error": "not a bot copy"}` in Mark's copy, 501 when the copy wasn't wired for them). Each answers at once and leaves the game work to the main thread:
  - `POST /coop/quit` `{"from": "Mark"}`: leave the lobby or run and quit, for `/bot stop`. Answers `{"reply": "Leaving the game and quitting."}`, the line Mark's chat shows.
  - `POST /coop/join-now` `{}`: look for the host's lobby now instead of at the next retry. Answers `{"ok": true}`.
  - `POST /coop/party` `{"op": "hello" | "open" | "turn" | "close", ...}`: a step of a planning session. Answers `{"ok": true}`, or `{"ok": false, "error"}` (still a 200) for an op it turned down, and 400 for a body that isn't a JSON object.
- `GET /state` and `POST /act` carry the same `chat` key as the tools, but peek: the messages stay unread, so a curl doesn't take them from the model, and their results don't mark the bot as thinking.

### Overlay (src/SpireMind/Game/ChatOverlay.cs)

- Built from stock nodes only (CanvasLayer, PanelContainer, VBoxContainer, RichTextLabel, LineEdit). No custom Node subclasses with `_Ready`/`_Process`/`_Input` overrides: a mod assembly loaded at runtime has no Godot source generators or script registration, so those overrides may never be called. Per-frame work hangs off the `SceneTree.ProcessFrame` signal ModEntry already uses, and signals connect with C# events or `Callable.From`.
- A `CanvasLayer` on layer 6 under `NGame.Instance`: game UI draws on layer 0 and the dev console on 10, so the box is above the one and under the other. It is added from the overlay's tick once NGame is ready (the mod initializer runs too early, inside `NGame._EnterTree`) and survives the menu, runs and new runs. `ProcessMode = Always`. The log ignores the mouse; only the open input box takes clicks.
- Keys come from a Harmony prefix on `NInputManager._UnhandledKeyInput` (`Patches/ChatInputPatches.cs`), which only sees keys the GUI didn't use. With the box closed, a fresh press of T with no modifiers opens it, is marked handled and isn't typed. With the box open, every key that reaches the prefix is kept from the game: Cmd or Ctrl plus a digit (which picks cards whatever has focus), F-keys, key releases. Escape, Up, Down and Tab are accepted in the LineEdit's `GuiInput`, and a second prefix on `NFeedbackScreenOpener._Input` keeps F2 from opening the feedback screen while typing. The game turns key releases into hotkey releases too, and its buttons click on release, so the overlay tracks every key whose press it took (the hotkey that opened the box included) and keeps that key's repeat and release from the game after the box has closed, however long it is held. A fresh press of such a key hands it back to the game. If the input patch didn't apply, the hotkey is polled on the tick instead (logged), and game hotkeys may then fire while typing. Known limit: a game hotkey still held when the chat hotkey is pressed loses its release (E down, T down, E up opens the box and End Turn doesn't fire until the next E press and release). Mouse clicks in the open box are still seen by the game's own mouse handlers, as a click on empty ground would be.
- The LineEdit keeps editing across Enter (`KeepEditingOnTextSubmit`) and opens with `GrabFocus()` plus `Edit()`, since the game's hotkey manager stands down only while the focused LineEdit is editing. Game screens release focus under an open box (the deck upgrade, transform, enchant and remove screens, which the bot's own picks open), so `Window.WindowInput` takes it back before each key. Switching to a controller closes the box and keeps the draft.
- Not a game screen: it never registers with `ActiveScreenContext`, `NModalContainer` or `NOverlayStack`, whose checks would disable the combat UI and confuse SpireMind's router. The bot keeps playing while the box is open.
- The game's look (`ChatTheme`): Kreon regular for text, Kreon bold for names, cream text, gold for the human's name and the box border, a black outline. The bot's name is in its character's `NameColor` (`Identity.NameColor`), else a built-in colour per character.
- The overlay never touches game types. ModEntry hands it hooks: the parent node, the theme, the bot's name colour, controller mode, the speech bubble callback, plus the human's name (`SPIREMIND_HUMAN_NAME`, else the OS user name capitalised).

### Speech bubbles (src/SpireMind/Game/SpeechBubbles.cs)

- The overlay hands every bot line to `SpeechBubbles.Say`, which cuts it into chunks of about 100 characters (the bubble's text box is a fixed 280x130 px), at a sentence end where it can, and queues them. `Tick` shows one at a time, each for about 0.12 s per letter as the game's `TalkCmd` does, between 1.5 and 6 s. At most 6 chunks wait; older ones are dropped, and the log always has the whole line.
- Where the bubble goes: over the character in combat (in `NCombatRoom.Instance.CombatVfxContainer`), at the character's thought bubble spot at a rest site, above the player's figure in a shop, beside the top-bar portrait anywhere else in a run, and at a fixed spot on the left of the screen under `NGame` outside a run (menus, character select). The colour is the character's `SpeechBubbleColor`, Purple for the Necrobinder, whose own falls back to the default look.
- A line outlives its room and its run: the bot often speaks and moves on in the same turn (a map node, an event's Leave, a reward, the last word before the main menu). A bubble the player can no longer see is taken down and shown again where it can be seen: one in the room when the room goes or is covered by rewards or the map, any bubble while the game fades the run's screen to black for travel (nothing new starts until the fade is over), and one over the character when the map or deck view hides the figure. Seen for under a second, it gets its whole time again; otherwise what was left; with under 0.6 s left it is dropped. Queued chunks carry on. On rewards and card picks over a finished fight the bubble sits over the character on the layer above the overlay. The thought cloud still goes with its room.
- The thought cloud: in combat, once `ChatHub.ThinkingSince` is 2.5 s old, an `NThoughtBubbleVfx` with "..." shows over the character. It goes away when the decision is made (a newer or no `ThinkingSince`), a speech bubble needs the spot, the bot is paused, or the fight ends. A decision handed over before the current room, or held for over 2 minutes, shows none: the session ended or the human took over by hand.
- Every game call is guarded: a failure costs the bubble and one log line, never the bridge.

### Persona (src/SpireMind/Game/Identity.cs)

- Polled once a second on the main thread. In a run the character is `LocalContext.GetMe(...).Character`. At character select (the top of `NGame.Instance.MainMenu.SubmenuStack` is an `NCharacterSelectScreen` with a `Lobby`) it is `Lobby.LocalPlayer.character`, the local player's pick. Random, nothing picked, and every other menu mean no character. A read that fails while a run loads or tears down keeps the last one.
- The name comes from `Character.Id.Entry` (IRONCLAD becomes Ironclad, and so on for Silent, Defect, Regent, Necrobinder), else the title without "The ". `Identity.NameColor` is the character's `NameColor`, for the chat log.
- When the character changes it sets `BotName` and replaces `Persona`:

```json
{
  "name": "Ironclad",
  "title": "The Ironclad",
  "id": "IRONCLAD",
  "pronouns": { "subject": "...", "object": "...", "possessive": "..." },
  "tone": "A terse, grim soldier.",
  "voice_lines": ["...", "..."]
}
```

- `pronouns` comes from `PronounSubject`, `PronounObject` and `PossessiveAdjective`, leaving out what can't be read. `tone` is our paraphrase per character (the list in `docs/chat-and-persona.md`).
- `voice_lines`: up to 15 short lines in the character's own voice, read once per character after `LocManager.Instance` is up. From the `characters` table, `<ID>.goldMonologue`, `aromaPrinciple`, `eventDeathPrevention`, `banter.alive.endTurnPing` and `banter.dead.endTurnPing`; from the `ancients` table, the character's lines to each Ancient, `<ANCIENT>.talk.<ID>.<i>-<j>[r].char` (an `r` marks a repeating dialogue, and the numbers have gaps wherever the Ancient speaks, so the keys are listed rather than probed), with the numbers probed. Each key is checked with `LocString.Exists` before it is read. Lines that are missing, empty, echo their key or hold a placeholder are dropped, the rest are cleaned to plain text, and the pick takes one source at a time, shortest first, skipping lines over 160 characters and repeats. Never epoch lore: it would spoil the timeline.

## Co-op

Each copy of the game runs its own SpireMind bridge. Mark plays in his own copy (the human copy, port 17772); each bot is a second copy on the same Mac, started with `--sts2bot=1` and its own port (17773 to 17775, up to three bots). Only bot copies play in a co-op run; the human copy's brain stays off in a co-op run or lobby (`docs/brain.md`, Co-op). Outside co-op Mark's window works exactly as in solo play, also while a bot copy is still running. Nothing goes over the game's network, so the mod stays `affects_gameplay: false`.

### The relay (src/SpireMind.Core/Coop/CoopRelay.cs)

The human copy runs a `CoopRelay` (`Game/CoopWiring.cs` starts it after the bridge and the chat box, so its first "joined the chat" line is never missed; a bot copy never relays). It works on its own pool tasks and only ever calls `http://127.0.0.1:<port>`, with no proxy and no redirects followed: a port that answers with a 3xx counts as not a bot. When the game quits (the scene tree root's `TreeExiting`, or process exit), the relay is stopped and its log goes quiet first. Whether the game is in co-op comes from the last snapshot's net type and from `Game/InstancePoll.cs`, which looks at character select and the run once a second (a net service of type Host or Client).

- **Finding bots.** The ports come from `SPIREMIND_BOT_PORTS` (such as `17773,17774`), else 17773 to 17775, plus the ports of the copies the game side started (`ICoopBots.Known`), minus its own. Unlinked ports get `GET /coop/info` every 5 s (0.5 s timeout). Only a copy that answers `role: "bot"` is linked, at most three. The first link in the relay's life starts reading after the bot's `last_seq`, so old lines aren't replayed, and says "Silent joined the chat (port 17773)."
- **The lobby nudge.** When Mark's copy enters a co-op lobby or run (`InstancePoll.InCoop` turns true on the frame tick, `CoopWiring.Tick`), the relay's `NudgeBots()` sends `POST /coop/join-now` to every linked bot, and one quiet try to each copy the game started that isn't linked yet. A bot then looks for the lobby at once rather than at its next retry, which after a run can be a minute away. The log says `coop: a co-op lobby opened here: asked 1 bot copy to look for it now`.
- **Names.** Each bot goes by its nameplate on Mark's screen in a local co-op game (`ICoopBots.NameOf`, "Ironclad", "Ironclad 2"), else its character, numbered from the second bot on the same character by port ("Ironclad 2"), else "The bot on 17773". Two bots never share a name. The chat labels, `/bots`, `/bot stop` and addressing all use it: "Ironclad 2, block" and `/model Ironclad 2 sonnet` reach only that bot, and in co-op a line that starts with such a name skips the other bots on that character too, since each would take a line that starts with its character as its own. A bot that hasn't reported a character yet is named from its status ("REGENT" becomes "Regent").
- **One worker per bot.** Each bot's HTTP calls run in order on one task: Mark's lines, commands and party lines, and a `GET /chat?since=` poll every second when nothing else waits. A poll never runs during a POST, so a command reply is never shown twice.
- **Mark's lines.** In co-op every line Mark types (not a command) is shown in his log as usual and posted to every bot as `{"from": "Mark", "text": ...}`. Each bot decides by name whether it is for it, as in What the player sees. Outside co-op a line goes only to the linked bot whose character it starts with ("Silent, ready?"); the rest are for Mark's own bot, as in solo play.
- **Bots' lines.** A polled bot line becomes a Remote bot line in Mark's log (`AddRemoteSay`, in the bot's colour by name) and a speech bubble over that bot's player on Mark's screen through `ICoopBots.ShowLine(netId, text)`. A bot's system lines (stops, the switch to the subscription, budget warnings) show labelled: "Silent: Silent paused.". Lines the bot logged from Mark, and Remote lines, are skipped.
- **Thought clouds.** Each poll reads the bot's `thinking`. When it changes, the relay calls `ICoopBots.Thinking(netId, on)`, which shows or takes away a thought cloud over that bot's player on Mark's screen (the game side's `RemoteBubbles.Thinking`). The game is only called on a change, and a bot that drops or a relay that stops takes its cloud down. A failure is logged once.
- **Commands.** In co-op, `/start`, `/stop`, `/pause`, `/resume`, `/budget`, `/model`, `/effort` and `/fast` go to every live bot while bots exist, and each bot's answer shows labelled with its character's name. A bot's name first sends to that bot only: `/model Silent sonnet`, `/help Silent`, in co-op or not. In co-op a name no bot plays gets "No bot is playing Defect right now. /bots lists them.". Plain `/help` runs here and ends with a note on how commands reach the bots. With no bots, or outside co-op without a linked bot's name, every command runs here, exactly as in solo play. The filter only queues work and returns at once. Nothing tells a bot that links later what was typed before: `/model` and `/effort` are in its own config.json by then, but `/fast on` is never saved, so a bot copy added or relaunched after it plays at normal speed until `/fast on` is typed again.
- **New commands** in the human copy:
  - `/bots` lists the bots, one line each, with where each one stands when it says so: "Silent on 17773 (NetId 1000, playing on API credit, deciding): joined; picked Silent; ready; waiting for the host to start." A bot in a run shows "in the run", and one whose join attempts stopped for a reason retrying can't fix shows "stopped trying to join (...)". Copies the game started that haven't answered yet show "(starting)" or "(not answering)".
  - `/bot add [Ironclad|Silent|Defect|Regent|Necrobinder|Random]` starts a bot copy through `ICoopBots.StartCopyAsync` and announces the game side's line when it is done (one start at a time; a start that hasn't finished after 3 minutes gets "The bot copy didn't come up within 3 minutes. /bots shows what is running; /bot add tries again." and frees `/bot add`).
  - `/bot stop [name]` asks bots to leave the lobby or run and quit. With a name (a nameplate name or a character, with or without "the") it sends only that bot `POST /coop/quit` through its worker, and the chat shows "Silent: Leaving the game and quitting.", then "Silent left, and its copy has quit." once its polls stop. Without a name, or with `all`, every bot goes: the copies the game started through `ICoopBots.StopAllAsync` (on the main thread; its line shows in chat, and after 30 s without one the chat says "The bot copies didn't all quit in time. /bots shows what is still running."), and copies started by hand (`scripts/coop-bot.sh`) through their own `/coop/quit`. A name nobody has gets "No bot is called X. /bots lists them." The game side's own `/botstop` still works as before.
  - `/party [on|off]` shows or sets whether bots hear each other.
  - `/plan [skip|show|on|off]` runs the bots' planning sessions: `/plan` starts one now (off combat), `/plan skip` ends the one running, `/plan show` shows the plan, `/plan on` and `/plan off` turn the automatic ones on or off. Planning sessions, below.
- **Party chat.** Each line a bot speaks is also posted to the other bots with `"teammate": true`, so they can plan builds together. It can't loop: only a bot's own spoken lines (`kind: "bot"`, not Remote) are forwarded, a relayed line is Remote in the receiving bot's log and never forwarded again, and each line is forwarded once. It can't run up cost: a teammate message never wakes a brain (`HasUnread` ignores it, and the API brain's wake check skips `teammate: true`), so it only rides along on a tool result or wait the bot was getting anyway. At most 10 lines a minute per bot are forwarded, and at most 20 wait in a bot.
- **Planning sessions.** The relay owns a `PartyConductor`, which runs short sessions in which the bots agree on their lanes for the act: at each act start while the Ancient's offer is up, around the middle of the act, before the boss, and on `/plan`. It sends its steps over each bot's worker (`POST /coop/party`), reads each bot's `party` report from the polls, takes Mark's lines into the bots' briefs, posts its own lines in Mark's chat ("Planning for act 2 (up to 2.5 minutes; the bots hold their Ancient picks). Mark, tell them what you're building, or /plan skip.", then "Party plan set: ..."), and writes the plan to `runs/party/plan.md` under the notes root. `docs/brain.md` (Planning sessions) has the whole flow.
- **Restarts and closed copies.** Three failed polls in a row: "Silent's copy stopped answering." once (or "Silent left, and its copy has quit." after a `/bot stop`), and the port goes back to probing. A copy that answers again with the same `session` resumes where it was ("Silent's copy is answering again."). A new `session`, or a `last_seq` below what was read, means it restarted: "Silent's copy restarted." and reading starts again from line 0.

`ICoopBots` (`src/SpireMind.Core/Coop/ICoopBots.cs`) mirrors the game side's static classes `SpireMind.Game.Coop.CoopBots` and `RemoteBubbles` (written on the Mac, under `src/SpireMind/Game/Coop/`) and the co-op nameplates, so Core stays game-free. `Game/CoopBotsAdapter.cs` is the only file on the relay's side that names those classes: it marshals `StartCopyAsync`, `StopAllAsync`, `ShowLine` and `Thinking` to the main thread without waiting, and refreshes `Known` and the nameplate names (`NameOf`, read through `CoopNames.NameOf`, which ModEntry passes in) once a second on the frame tick. If the game side can't be used, `TryCreate` logs why and returns null: the relay then still links copies started by hand by probing their ports, `/bot add` answers "This build can't start bot copies; start one with scripts/coop-bot.sh.", and no bubbles, clouds or nameplate names come from the game.

A bot copy reports who it is on `/coop/info` and `/chat`: `role: "bot"`, its NetId (`Game/InstancePoll.cs` reads it once a second: the lobby's net service at character select, `LocalContext.NetId` in a run), its character (`ChatHub.BotName`), which brain plays, whether it is deciding and where it stands. The relay labels lines with the bot's name and finds the right player by NetId.

`Game/BotSelf.cs` wires a bot copy's side (the human copy is never wired). Twice a second on the main thread it takes a snapshot of the game side's `LobbyDriver.Status`, `LobbyDriver.Character`, `LobbyDriver.InRun` and `JoinWatcher.Stopped` into a `BotStatus`; the bridge's worker threads only read that snapshot. `POST /coop/quit` queues `CoopBots.RequestQuit("Mark asked with /bot stop")` for the main thread and answers at once; if the last snapshot said the game side doesn't run this copy as a bot copy (`CoopBots.IsBotCopy` false), it answers "This copy can't leave and quit by itself (its log says why); close its window." instead. `POST /coop/join-now` queues `JoinWatcher.RetryNow()`.

### Launcher contract

Whatever starts a bot copy (`scripts/coop-bot.sh`, or `CoopBots.StartCopyAsync` from `/bot add`) must start a second copy of the game without Steam, with the flags `--force-steam off --clientId <1000, 1001 or 1002> --fastmp join --sts2bot=1` and the environment variable `SPIREMIND_PORT=<17773, 17774 or 17775>`, one pair per bot. `SPIREMIND_CONFIG_DIR` is optional: unset, a bot copy keeps its own files in `~/.config/spiremind/bot-<port>/` (config.json, transcripts, fights.jsonl, autostart). The launcher writes nothing else: the API key, the shared config.json, spend.json and the locks stay in `~/.config/spiremind/`, which every copy reads, and the bot's run journal goes in `runs/bot-<port>/current.md` under the notes root. A port outside `SPIREMIND_BOT_PORTS` (or 17773 to 17775 when that is unset) is only found if the game side lists it in `CoopBots.Known`.

A copy that runs with Steam is always the human copy, whatever its command line says, so a stray `--sts2bot=1` in Steam's launch options can't turn Mark's own game into a bot copy. `InstanceRole.Detect` asks `SteamInitializer.Initialized` (settled before mods load) only when the bot flag is set; with Steam on, or when that check throws, the flag is ignored and ModEntry logs an error: "role: --sts2bot=1 is on the command line, but this copy runs with Steam, so the flag is ignored and this copy runs as the human copy. A bot copy is started without Steam (--force-steam=off)."

### Trying it without the game

The dev host runs fake copies on localhost:

```bash
scripts/dev-host.sh 17773 --bot --character Silent --echo   # a fake bot copy that answers "Heard you, Mark."
scripts/dev-host.sh --relay --bot-ports 17773                # a fake human copy: type hello, /pause, /bots, /bot add Regent
```

The relay prints relayed lines as `chat Silent (relayed): ...`, bubbles as `bubble over 1000: ...` and clouds as `thought cloud over 1000`. `/bot stop Silent` makes the fake bot copy quit, and `/bots` shows its status line ("a dev host: no game, so no lobby").
